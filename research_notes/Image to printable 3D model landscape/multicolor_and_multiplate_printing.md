# Multi-color / multi-material FDM and multi-plate (split-and-assemble) printing: encoding, Python generation, segmentation, partitioning

Research date: 2026-11-08. Scope: how color and multi-part information must be encoded for PrusaSlicer, OrcaSlicer, Bambu Studio and Cura; how to generate those files from Python on an Apple Silicon Mac; how to turn a textured/vertex-colored mesh into discrete filament regions; how to split a model into plates/parts with alignment features. Evidence labels used throughout: **[primary]** = read directly from spec, source code, vendor page or official wiki; **[secondary]** = forum, review, blog, aggregator or search snippet; **[unverified]** = claim I could not confirm. Repo stars/push dates were read from the GitHub API on 2026-11-08 unless stated; PyPI versions/dates from the PyPI JSON API on the same day. Note: web-search budget ran out mid-task, so later gaps were closed with direct fetches of source files and official pages only; a few vendor pages (Bambu store, Anycubic, Creality) refused automated fetches.

## Key question 1: Hardware/process context in 2026 and what it implies for colors per layer

### Takeaway
Two architectures dominate: single-nozzle filament switchers (Bambu AMS family, Prusa MMU3, Anycubic ACE, Creality CFS) which must flush the nozzle on every change and therefore punish many color changes per layer, and multi-toolhead machines (Prusa XL, Snapmaker U1, Bambu H2D's dual nozzle) which swap in seconds with little or no purge. Model-side, the wiki-documented rule is that a layer with N filaments costs N-1 changes, so the generator should minimize distinct colors per layer and cluster color changes vertically.

### Cited Findings
- **[primary]** Bambu's Filament Change Procedure on single-nozzle printers has three stages: flushing ("the extruder pushes or 'Flushes' the old filament through the nozzle until the filament being extruded is purely the new filament"), wiping, and priming on a prime tower; "The color of the extruded filament is the main factor that determines the volume of material that must be extruded during a flush... Darker colors need a higher volume flush to switch to lighter colors, and lighter colors need less to switch to darker colors." A 0.2 mm nozzle "may take significantly longer to complete the Flushing step than a standard 0.4 mm nozzle." — [Bambu Lab Wiki: Reduce wasting during filament change](https://wiki.bambulab.com/en/software/bambu-studio/reduce-wasting-during-filament-change)
- **[primary]** "In almost all cases, the number of filament changes on a single layer is one less than the number of filaments on that layer. This is because the last filament on a given layer is printed first on the next layer." Increasing layer height "will directly reduce filament waste" because it reduces layer count. — [Bambu Lab Wiki](https://wiki.bambulab.com/en/software/bambu-studio/reduce-wasting-during-filament-change)

### Inferences
- For a single-nozzle target (AMS/MMU/ACE/CFS), the generator should (a) cap distinct filaments per layer (every extra filament on a layer costs a flush of hundreds of mm3 and tens of seconds), (b) keep color changes vertically contiguous so the prime tower can stop early, and (c) prefer 2.5D color (color regions that are vertically separated) over interleaved 3D color where the design allows.
- For toolchangers (XL, U1), the per-layer color count is nearly free in waste terms, so the same mesh can be sliced with far more colors per layer; the generator can treat "max colors per layer" as a printer-profile parameter.
- Practical color counts: 4 per unit for AMS-class systems, 5 for MMU3, 4 heads for U1, up to 5 for XL; chaining AMS units raises the palette to 16+ but does not change the per-layer cost model.

### Gaps
- Official Bambu AMS 2 Pro / AMS HT chaining limits and official Anycubic/Creality spec sheets could not be fetched (HTTP 402/403/429/404); only secondary numbers are recorded.
- No controlled, independent gram-per-swap comparison across AMS, MMU3, ACE Pro and CFS was found.

## Key question 2: How to encode color for slicers (multi-body, per-triangle paint, 3MF materials extension, per-layer M600, vertex colors/textures) and which is most portable

### Takeaway
Three encodings actually drive slicers: (1) multi-body objects with an extruder index in slicer-specific config files (most portable), (2) per-triangle paint strings (`paint_color` in Bambu/Orca, `slic3rpe:mmu_segmentation` in PrusaSlicer) whose bit format is fully readable in the open-source slicer code and is deterministic but slicer-family specific, and (3) the standard 3MF Materials extension, which Bambu Studio/OrcaSlicer map to object-level extruders on import while I found no evidence that PrusaSlicer or Cura use it. Vertex colors/textures are ignored by slicers except Bambu Studio's colored-OBJ importer, which converts them into paint strings.

### Cited Findings

**(b) Per-triangle paint format - verified from source**
- **[primary]** Bambu Studio/OrcaSlicer store paint in the triangle attribute `paint_color` (`static constexpr const char* MMU_SEGMENTATION_ATTR = "paint_color";`); a companion attribute `face_property` exists; PrusaSlicer uses `slic3rpe:mmu_segmentation` in namespace `xmlns:slic3rpe="http://schemas.slic3r.org/3mf/2017/06"` with a model-level `<metadata name="slic3rpe:MmPaintingVersion">`. — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp); [OrcaSlicer 3mf.cpp (Prusa format)](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/3mf.cpp)
- **[primary]** Bit layout, from `TriangleSelector::serialize()`: "Each original triangle of the mesh is assigned a number encoding its state or how it is split. Each triangle is encoded by 4 bits (xxyy) or 8 bits (zzzzxxyy): leaf triangle: xx = EnforcerBlockerType (Only values 0, 1, and 2. Value 3 is used as an indicator for additional 4 bits.), yy = 0; leaf triangle: xx = 0b11, yy = 0b00, zzzz = EnforcerBlockerType (subtracted by 3); non-leaf: xx = special side, yy = number of split sides". Children of a split triangle are "Serialized in reverse order for compatibility with PrusaSlicer 2.3.1". In OrcaSlicer main, states >= 18 add a second nibble: "Store '11' plus 4 bits of (n-3), which covers states 3..17. State 18 and above set that nibble to 0b1111 and store (n-18) in a second nibble." Only triangles that are split or non-NONE are emitted. — [OrcaSlicer TriangleSelector.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/TriangleSelector.cpp)
- **[primary]** State enum: `NONE=0, ENFORCER=1, BLOCKER=2, Extruder1=ENFORCER, Extruder2=BLOCKER, Extruder3...`; in OrcaSlicer main `ExtruderMax = Extruder32`. — [OrcaSlicer TriangleSelector.hpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/TriangleSelector.hpp)
- **[primary]** Hex string conversion: `get_triangle_as_string` reads the bitstream 4 bits at a time, LSB-first within a nibble (`for (int i=3; i>=0; --i) { next_code <<= 1; next_code |= bitstream[offset+i]; }`), maps 0-9 and A-F, and `out.insert(out.begin(), digit)` so the string is written most-recent-nibble first; `set_triangle_from_string` reverses this (iterates the string from the end). — [OrcaSlicer Model.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Model.cpp)
- **[primary]** Whole-triangle strings per filament are tabulated in `CONST_FILAMENTS`: `"", "4", "8", "0C", "1C", "2C", "3C", "4C", "5C", "6C", "7C", "8C", "9C", "AC", "BC", "CC", "DC", "EC", "0FC", "1FC", ... "EFC"` (index = 1-based filament; index 0 = unpainted). This table is used by Bambu's colored-OBJ importer (`obj_import_vertex_color_deal`). — [OrcaSlicer Model.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Model.cpp)
- **[primary]** Deserialization reconstructs splits geometrically from the original mesh (`set_division` + `perform_split`), so split codes are only meaningful relative to the exact triangle; malformed data is dropped with a warning ("dropping malformed paint data of triangle"). — [OrcaSlicer TriangleSelector.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/TriangleSelector.cpp); [OrcaSlicer Model.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Model.cpp)
- **[primary]** Painting semantics in PrusaSlicer: "During slicing, the painted regions are cleverly extended inwards... The regions painted at the side walls are expanded inwards up to maximum mmu_segmented_region_max_width"; "The painting only affects the slicing result, the model itself is not altered and the colored 'parts' cannot be exported separately"; "thin non-printable regions created during segmentation are thus detected and merged with the neighboring region, changing its color"; "The multi-material painting is limited to 16 extruders"; "Multi-material painting cannot be combined with XY size compensation." — [Prusa KB: Multi material painting](https://help.prusa3d.com/article/multi-material-painting_262620)
- **[primary]** PrusaSlicer 2.7.4 release notes: "Objects from 3MFs generated by BambuStudio now retain multimaterial painting when loaded." — [PrusaSlicer release 2.7.4](https://github.com/prusa3d/PrusaSlicer/releases/tag/version_2.7.4)
- **[secondary]** Community confirmation of the attribute values: a Prusa forum example shows `<triangle v1=.. v2=.. v3=.. slic3rpe:mmu_segmentation="4"/>`, and a 2026 Google Groups thread observes simple values "4", "8", "0C", "1C" with split patterns unclear to the poster. — [Prusa forum](https://forum.prusa3d.com/forum/prusaslicer/import-multimaterial-within-one-file/); [Google Groups](https://groups.google.com/g/3d-printing-tips--tricks/c/QBjwUy1Xufo)
- **[secondary]** Open-source parsers/writers of the paint format: Go module `github.com/BryanSmee/bl_to_std` (GPL-3.0, v0.0.0 published 2026-10-12, 0 stars) implements "the codec for the per-triangle painting data stored by Bambu Studio and OrcaSlicer in 3MF model files" and converts Bambu project 3MFs "into standard 3MF projects for other multi-filament printers" such as the Snapmaker U1. — [pkg.go.dev](https://pkg.go.dev/github.com/BryanSmee/bl_to_std/pkg); [GitHub](https://github.com/BryanSmee/bl_to_std). **(a) Multi-body objects with extruder assignment**
- **[primary]** PrusaSlicer format: `Metadata/Slic3r_PE.config` (print config) and `Metadata/Slic3r_PE_model.config`; the model config writes `<object id=.. instances_count=..>` with `<metadata type="object" key="name" .../>` and all object config keys, then per volume `<volume firstid=".." lastid="..">` (triangle index range inside the object's single mesh) with `<metadata type="volume" key="volume_type" value="ModelPart|ParameterModifier|...">`, `key="matrix"`, source-file keys, and the volume's config keys (which include `extruder`). — [OrcaSlicer 3mf.cpp (Prusa format)](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/3mf.cpp)
- **[primary]** Bambu/Orca format: `Metadata/model_settings.config` writes `<config>` containing `<object id=".." auto_drop="..">` with `<metadata key="name"/>` and every object config key (e.g. `extruder`), then `<part id=".." subtype="normal_part|modifier_part|...">` with `key="name"`, `key="matrix"` (16 floats), `source_file`/`source_object_id`/`source_volume_id`/`source_offset_*`, every volume config key (e.g. `extruder`), and a `<mesh_stat .../>`; then `<plate>` blocks with `plater_id`, `plater_name`, `locked`, `bed_type`, `print_sequence`, `filament_map_mode`, `filament_map`, and `<model_instance>` children carrying `object_id`, `instance_id`, `identify_id`; `<assemble>`/`<assemble_item>` blocks; `Metadata/cut_information.xml` for cut history. The root `3D/3dmodel.model` declares `xmlns:BambuStudio="http://schemas.bambulab.com/package/2021"` and, when sub-models are used, `xmlns:p="...production/2015/06" requiredextensions="p"`. — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp)
- **[primary]** Bambu's part-level extruder fallback: on import, objects with no `extruder` get `1`, and a volume whose extruder is missing/zero inherits (`mo->config.set_key_value("extruder", new ConfigOptionInt(1))`, `mv->config.erase("extruder")`). — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp). The dev.to write-up describes the same resolution order (painted state > part extruder > object extruder > filament 1) and shows `project_settings.config` as JSON with `"filament_colour": ["#FFFFFF", "#D32F2F"]` (AI-assisted article, **[secondary]**). — [dev.to: What's actually inside a Bambu/Orca 3MF](https://dev.to/joyfunc/whats-actually-inside-a-bambuorca-3mf-24p0)
- **[primary]** Cura writes per-object settings into the 3MF as `cura:`-namespaced metadata (`"cura": "http://software.ultimaker.com/xml/cura/3mf/2015/10"`), explicitly adding `extruder_nr` when `machine_extruder_count > 1`; the reader applies `extruder_nr` through `ExtruderManager.getExtruderStack(int(setting_value))`; libSavitar parses these from `<metadatagroup><metadata .../>` under each `<object>`. No occurrence of "color", "pid" or "basematerial" exists in Cura's ThreeMFReader.py. — [Cura ThreeMFWriter.py](https://github.com/Ultimaker/Cura/blob/main/plugins/3MFWriter/ThreeMFWriter.py); [Cura ThreeMFReader.py](https://github.com/Ultimaker/Cura/blob/main/plugins/3MFReader/ThreeMFReader.py); [libSavitar SceneNode.cpp](https://github.com/Ultimaker/libSavitar/blob/main/src/SceneNode.cpp)
- **[primary]** PrusaSlicer KB: "3MF files natively support multiple objects in a single file" and multi-material models "should be automatically recognized and loaded correctly"; when loading several STLs it "will ask you if it should represent the loaded models as one single object with multiple parts" (requires a multi-material printer preset). — [Prusa KB: Importing multi-material model](https://help.prusa3d.com/article/importing-multi-material-model_121191); tool assignment per feature/part: [Prusa KB: Assigning tools/colors/extruders](https://help.prusa3d.com/article/assigning-tools-colors-extruders_124811)
- **[primary]** Bambu Studio treats a 3MF as its own project only when the root model's `<metadata name="Application">` starts with `BambuStudio-` or `OrcaSlicer-` (or an `OrcaSlicer` version tag is present, "written from OrcaSlicer 2.3.2 onwards"); otherwise it logs "found 3mf from other vendor, split as instance" and splits multi-instance objects into separate objects. — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp)

**(c) 3MF Materials & Properties extension**
- **[primary]** Core spec property rules: object `pid`/`pindex` "to be applied to the entire object, except where overridden by a descendant element, such as a <triangle>"; "If this object contains any triangles with assigned properties, the object MUST specify pid and pindex"; "Producers MUST NOT assign pid or pindex attributes to objects that contain components"; triangle `p1,p2,p3` override per vertex, "A consumer that cannot create property gradients MUST apply the p1 property to the entire triangle. A consumer that cannot use properties on a per-triangle basis MUST ignore the triangle properties and use the <object> level property instead"; for `<basematerials>` "p1, p2 and p3 MUST be equal or unspecified"; "A producer MUST NOT assume that displaycolor has any effect on the printed part." — [3MF Core Specification (GitHub)](https://github.com/3MFConsortium/spec_core/blob/master/3MF%20Core%20Specification.md)
- **[primary]** Materials extension: namespace `http://schemas.microsoft.com/3dmanufacturing/material/2015/02` (prefix `m`); "This extension MUST be used only with Core specification 1.2"; `<m:colorgroup>` holds `<m:color value="#RRGGBBAA">` entries ("what most 3D formats call 'vertex colors'"); `<multiproperties pids="...">` with `<multi pindices="...">`, where "The pids list MUST NOT contain more than one reference to a material (base or composite). The pids list MUST NOT contain more than one reference to a colorgroup. The pids list MUST NOT contain any references to a multiproperties"; also texture2d/texture2dgroup, composites, PBR display properties. — [3MF Materials Extension (GitHub)](https://github.com/3MFConsortium/spec_materials/blob/master/3MF%20Materials%20Extension.md); PDF v1.2.1 (2025-02): [3mf.io](https://3mf.io/wp-content/uploads/sites/106/2025/02/3MF_Materials_Extension_v1_2_1.pdf); the consortium's spec page lists Materials v1.2.1 (02/27/2025), Core v1.3.0 and the suite as ISO/IEC 25422:2025 — [3mf.io/spec](https://3mf.io/spec/)
- **[primary]** Bambu Studio/OrcaSlicer import standard color groups: the parser handles `m:colorgroup`/`m:color`, builds `color_group_id_to_extruder_id_map` (a new extruder index for each distinct color value, in encounter order), and sets the object-level `extruder` from the object's `pid` (`model_object->config.set_key_value("extruder", ...)`). No per-triangle `p1` handling was found in this path. — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp)
- **[secondary]** Users report Bambu Studio 2.5 added a "Standard 3mf Import color" dialog that "adds a new grey filament spool" and asks on every import; an OpenSCAD list thread says "the latest release (2.5) of Bambu Studio supports importing color information in a .3mf file". — [Bambu forum](https://forum.bambulab.com/t/how-to-disable-standard-3mf-import-color/241644); [OpenSCAD list](https://lists.openscad.org/empathy/thread/VRIEOLXTTAY6Z4CVJ2FD26E4EN37NQHI)
- **[primary, absence of evidence]** The Prusa-format importer copy in OrcaSlicer contains no `basematerials`/`colorgroup`/`pid` handling, and PrusaSlicer 2.9.0-2.10.0 release pages contain no 3MF+color items. The printer automatically pauses the print as soon as it reads the color change in the G-code (M600 command)"; "Use filaments of the same type. Always mix PLA with PLA, PETG with PETG." Preview colors "do not affect the generated G-code." — [Prusa KB: Color change](https://help.prusa3d.com/article/color-change_1687)
- **[primary]** Bambu's exporter writes a `custom_gcode_per_print_z` file for per-height custom G-code (`_add_custom_gcode_per_print_z_file_to_archive`). — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp)

**(e) Vertex colors / textures**
- **[primary]** Bambu Studio "supports importing geometric data and color information from Obj files"; an import dialog "automatically performs the best color matching" to filaments with manual override. — [Bambu Lab Wiki: Import OBJ](https://wiki.bambulab.com/en/software/bambu-studio/import_obj). In code, `Model::obj_import_vertex_color_deal` takes per-vertex filament IDs, sets the object/volume `extruder` to `first_extruder_id`, and for each face emits either a whole-triangle `CONST_FILAMENTS` string (3 same colors) or a split encoding (`_3_DIFF_COLOR`, `_2_SAME_1_DIFF_COLOR`) computed from triangle geometry. — [OrcaSlicer Model.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Model.cpp)
- **[secondary]** Forum experience: OBJ import "reliable for face-level colors" while 3MF color was "more limited and less predictable"; one claim that Bambu "only reads two kinds of color information from an .obj file" including per-vertex `v x y z r g b` (unverified). — [Bambu forum: colored OBJ](https://forum.bambulab.com/t/import-colored-obj-file/164083); [printpal AMS converter](https://printpal.io/tools/ams-converter)
- **[primary]** trimesh's 3MF loader reads only vertex `x,y,z` and triangle `v1,v2,v3` (no colors), confirming that generic tooling also drops 3MF color. — [trimesh threemf.py](https://github.com/mikedh/trimesh/blob/main/trimesh/exchange/threemf.py)

### Inferences
- Most deterministic AND most portable: one watertight body per color, each a separate `<object>` with a build item, plus slicer-specific sidecar config (`Slic3r_PE_model.config` for PrusaSlicer, `model_settings.config` + `project_settings.config` for Bambu/Orca, `cura:extruder_nr` metadata for Cura). All four slicers load multi-object 3MF; only the extruder mapping differs.
- Per-triangle paint is the right choice when color boundaries cross a single shell (avoids boolean splitting), and it is bit-exact reproducible: for a mesh pre-subdivided so every triangle has one color, write `paint_color`/`slic3rpe:mmu_segmentation` = `CONST_FILAMENTS[k]` ("4" for filament 1, "8" for 2, "0C".."EC" for 3-17, "0FC".. for 18+). Stay within 16 filaments for PrusaSlicer compatibility. Avoid emitting split codes from Python; subdivide the mesh instead.
- The Materials extension is the only standard route, but today only the Bambu/Orca family demonstrably maps it (object-level only) and it changes filament lists on import; treat it as a courtesy layer for viewers, not as the driver for slicing.

### Gaps
- Whether Bambu Studio honors `model_settings.config` for files whose `Application` metadata is not `BambuStudio-`/`OrcaSlicer-` (i.e., whether a generator must spoof that metadata) was not traced to the exact code branch.
- PrusaSlicer's current (2.9/2.10) handling of 3MF Materials extension colors: no evidence either way.
- Whether Bambu Studio proper (not OrcaSlicer main) also uses the `ExtruderMax = Extruder32` two-nibble encoding: not checked in the bambulab/BambuStudio repo.

## Key question 4: Converting a textured or vertex-colored mesh into N discrete printable color regions

### Takeaway
No open-source, maintained Python tool does the full "texture -> N watertight per-filament shells" job; the pieces exist (trimesh texture-to-vertex-color sampling, palette quantization, face grouping, manifold3d booleans), the slicers themselves do the last mile (Bambu's colored-OBJ importer converts vertex colors into paint; PrusaSlicer/Bambu extend painted surface patches inward and merge thin regions), and the only turnkey tools are paid Blender add-ons or image-to-layer (HueForge-style) generators.

### Cited Findings
- **[primary]** Slicer-side behaviour that a generator can rely on: painted regions are "extended inwards"; top/bottom painted regions extend by `top_solid_layers`/`bottom_solid_layers`, side-wall regions "up to maximum mmu_segmented_region_max_width"; thin non-printable regions are "merged with the neighboring region"; "detect thin walls" is advised for thin features. — [Prusa KB: Multi material painting](https://help.prusa3d.com/article/multi-material-painting_262620)
- **[primary]** Bambu Studio's colored-OBJ importer is effectively a vertex-color-to-paint converter: per-vertex filament IDs -> whole-triangle or split paint codes, with a color-matching dialog to the loaded filaments. — [OrcaSlicer Model.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Model.cpp); [Bambu Wiki: Import OBJ](https://wiki.bambulab.com/en/software/bambu-studio/import_obj)
- **[primary]** trimesh building blocks: `TextureVisuals.to_color()` -> `ColorVisuals(vertex_colors=...)` from UV lookup; `Trimesh.split()` by face connectivity; boolean `union/difference/intersection` with pluggable engines (manifold3d is one). — [trimesh texture.py](https://github.com/mikedh/trimesh/blob/main/trimesh/visual/texture.py); [trimesh base.py](https://github.com/mikedh/trimesh/blob/main/trimesh/base.py)
- **[secondary]** "Comfy3D Texture Splitter" node: "pure trimesh and numpy", samples each face's color through UVs, quantizes, and writes "each color group... as its own submesh" into a multi-part GLB. — [comfy.icu node page](https://comfy.icu/node/Comfy3D-Texture-Splitter)
- **[secondary]** Paid Blender add-ons: "AMS Splitter" reads a Base Color texture, detects main colors, converts them into separate material regions, and describes the core problem as meshes "made of many open, disconnected shells, which slicers handle poorly", fixing it by rebuilding "one clean, watertight solid"; "3MF Magic Solver" imports/paints/exports multicolor 3MF. Licenses not stated (Superhive marketplace). — [AMS Splitter](https://superhivemarket.com/products/ams-splitter); [3MF Magic Solver FAQ](https://superhivemarket.com/products/3mf-magic-solver/faq)
- **[primary]** colorplate 0.6.0 (PyPI 2026-06-09, MIT, Python 3.10+, CLI + web GUI): "Turn SVG/PNG artwork into layered, gap-free multicolor STL plates for face-down multi-material 3D printing (toolchanger / MMU)" — one watertight STL per color sharing an origin. — [PyPI colorplate](https://pypi.org/project/colorplate/)
- **[primary]** AutoForge 2.2.0 (PyPI 2026-10-16; CC BY-NC-SA 4.0 for the tool, prints MIT; 262 stars): image -> layered model via "a learned optimization strategy with a Gumbel softmax formulation" assigning materials per layer; outputs `final_model.stl`, HueForge `project_file.hfp`, `swap_instructions.txt`; "FlatForge" mode outputs separate STLs per color; runs on "Apple Silicon (MPS / Apple Metal)"; defaults 75 max layers at 0.04 mm, `--pruning_max_colors` default 100; examples capped at 8 colors / 20 swaps using 27 Bambu PLA filaments. No 3MF/Bambu project output. — [AutoForge GitHub](https://github.com/hvoss-techfak/AutoForge); [PyPI AutoForge](https://pypi.org/project/AutoForge/)
- **[secondary]** Kromacut: "Open source HueForge alternative" in TypeScript with "Download STL or Download 3MF" and Beer-Lambert layer optics; Lumina Layers: GPL-3.0 Python project (3MF support unconfirmed). — [Kromacut](https://github.com/vycdev/Kromacut); [Lumina Layers](https://github.com/MOVIBALE/Lumina-Layers)
- **[primary]** FullSpectrum (ratdoux/OrcaSlicer-FullSpectrum, AGPL-3.0, 779 stars): fork of Snapmaker Orca adding "virtual mixed-color filaments" that "create new colors by alternating layers between physical filaments", targeting the Snapmaker U1; Hackaday (2026-03-17) recommends 0.08-0.12 mm layers because "the standard 0.2 mm height introduces striping". OpenVCAD's "Prusa ColorMix" / Orca "FullSpectrum" compilers emit such recipes (max 3 components per recipe) and write a DeltaE fit report. — [FullSpectrum repo](https://github.com/ratdoux/OrcaSlicer-FullSpectrum); [Hackaday](https://hackaday.com/2026/03/17/fullspectrum-is-like-hueforge-for-3d-models-but-bring-your-toolchanger/); [OpenVCAD docs](https://matterassembly.org/OpenVCAD-Docs/v3/guides/compilers/slicer-project.html)
- **[older, primary]** "Colored Fused Filament Fabrication" (Song, Martinez, Bedell, Vennin, Lefebvre; arXiv 2017, ACM TOG 2019) uses "off-the-shelves nozzles that are designed to mix multiple filaments in a small melting chamber" and splits each layer into constant-color strata whose thickness sets perceived color; IceSL presents it as its color-mixing feature (freely downloadable, not open-source as far as found). Not applicable to AMS-class hardware. — [arXiv 1709.09689](https://arxiv.org/abs/1709.09689); [IceSL color mixing](https://icesl.loria.fr/pages/features/color-mixing)
- **[older, secondary]** Dual-Color Mixing for FDM (CGF 2014) produces continuous tone with two heads via geometric offsets; a DTU 2022 poster segments an input image by color thresholds to avoid purge towers; MeshMixer 3.0 (2016, closed source) added multi-material part assignment. — [Dual-Color Mixing PDF](https://cg.ivd.kit.edu/publications/2014/DCM/DualColorMixing.pdf); [DTU poster](https://people.compute.dtu.dk/jerf/papers/posters/colorfdm_poster_ASPE2022.pdf); [Fabbaloo on MeshMixer 3.0](https://www.fabbaloo.com/2016/01/meshmixer-30-enables-multi-material-3d-printing)

### Inferences
- A deterministic pipeline on the user's Mac: (1) `TextureVisuals.to_color()` or direct UV sampling -> per-face colors (area-weighted sample at face centroid/barycentric points), (2) quantize to the printer palette in a perceptual space (the 3MF spec's own guidance is to interpolate in sRGB but blend in linear RGB), (3) label faces, (4) either emit paint strings per face (surface-only; let the slicer extend inward and merge thin regions) or build per-color solids by offsetting the labeled surface inward by at least the slicer's `mmu_segmented_region_max_width` and booleaning against the base body with manifold3d, (5) export via lib3mf or a custom writer.
- Minimum region size: because PrusaSlicer merges "thin non-printable" segmented regions and Bambu flushes per change, regions narrower than roughly one extrusion width or smaller than a few mm2 should be merged into their neighbour before export; exact thresholds are not published (see Gaps).
- Overhang boundaries: painted color only affects which filament prints a region; it does not create geometry, so color boundaries on overhangs do not change support needs, but per-color shells (option 4b) do create internal faces and can create tiny unsupported slivers at boundaries - prefer paint for complex boundaries and shells for large, simple regions.

### Gaps
- No recent (2024-2026) academic method or open-source tool was found that converts arbitrary textures to N discrete filament regions for AMS-style printing; searches surfaced only layer-stacking (HueForge-style) and mixing-nozzle work.
- No published numeric guidance on minimum paintable region size relative to nozzle diameter; only PrusaSlicer's qualitative merge rule.
- The licenses and internals of AMS Splitter / 3MF Magic Solver are unknown (paid, closed).

## Key question 5: Multi-plate / split-and-assemble: cutting, connectors, tolerances, academic partitioning

### Takeaway
Slicer cut tools (PrusaSlicer and Bambu Studio) offer planar and dovetail cuts with plug/dowel/snap connectors and orientation options, but neither documents a recommended tolerance; Python can reproduce planar cuts deterministically with trimesh `slice_mesh_plane(cap=True)` or manifold3d `split_by_plane`, and the only open-source automatic partitioner found is pychop3d (MIT, Python implementation of Chopper, small and seemingly stale). Published clearance numbers come from maker guides and vary; all sources say to calibrate.

### Cited Findings
- **[primary]** PrusaSlicer Cut tool: connectors "Plug" ("adds a plug to the side of the cut and subtracts the space for it from the other side"), "Dowel" ("subtracts the pin from both sides and generates an extra object to print as the connector"), "Snap" ("Adds a snap-fit connector on one side and subtracts the space to fit it on the other side"); "The standard connector is a circular prism plug"; style/shape/depth/size/rotation adjustable; part orientation options keep/place-cut-on-bed/flip; connectors unavailable in Dovetail mode; the article does not mention tolerance. — [Prusa KB: Cut tool](https://help.prusa3d.com/article/cut-tool_1779)
- **[primary]** Bambu Studio Cut tool: Planar mode and Dovetail mode (parameters Depth, Width, Flap angle, Groove angle - "Increasing the angle creates a more pronounced interlock"); connectors "Plug, Dowel and Snap"; cut into "multiple objects (default) or a multi-part object"; post-cut orientation "Keep orientation, Place on cut and Flip"; right-click reassigns parts between Object A/B; a non-manifold warning may appear after dovetail cuts. — [Bambu Lab Wiki: Cut tool](https://wiki.bambulab.com/en/software/bambu-studio/cut-tool)
- **[secondary]** Tolerance semantics: a Bambu forum post describes cut-connector tolerance as working "like the X-Y hole compensation feature"; Prusa forum users report conflicting behaviour ("the cut holes were the dowel size plus the tolerance" vs "regardless of the tolerances, the cut and the plug/dowel/snap always come out the same size"). — [Bambu forum: Cut menu](https://forum.bambulab.com/t/cut-menu-in-studio/152029); [Prusa forum: Cut Tool doesn't change part size](https://forum.prusa3d.com/forum/prusaslicer/cut-tool-doesnt-change-part-size/)
- **[secondary]** Clearance guidance: a vendor guide designs a 10 mm shaft's hole at 10.5 mm "to achieve the 0.4mm clearance after the 0.3mm printing under-size", and gives "Metal pin into printed hole 0.1-0.3mm"; a MakerWorld test model lists sliding/rotating fits at "+0.20mm or higher" and press fits at nominal; Make: found non-round pins and chamfers make press fits more forgiving; all recommend printing a graduated gauge in the final orientation/settings. — [Sovol tolerances guide](https://www.sovol3d.com/blogs/news/fdm-3d-printing-tolerances-clearances-how-to-design-parts-that-fit); [MakerWorld Tolerance & Fit Test](https://makerworld.com/en/models/2820462-tolerance-fit-test); [Make: press-fit tips](https://makezine.com/article/digital-fabrication/3d-printing-workshop/tips-3d-printing-press-fit-parts/)
- **[primary]** Python cutting primitives: trimesh `slice_mesh_plane(mesh, plane_normal, plane_origin, cap=False)` ("If True, cap the result with a triangulated polygon"); manifold3d `split_by_plane(normal, origin_offset)` returns both halves, `trim_by_plane` one half, plus `decompose`, `hull`, `batch_boolean`. PrusaSlicer CLI `--cut <Z>` cuts at a Z height; OrcaSlicer CLI documents no cut flag. — [trimesh intersections.py](https://github.com/mikedh/trimesh/blob/main/trimesh/intersections.py); [manifold3d.cpp](https://github.com/elalish/manifold/blob/master/bindings/python/manifold3d.cpp); [prusa-slicer(1)](https://dyn.manpages.debian.org/trixie/prusa-slicer/prusa-slicer.1); [Orca CLI transform](https://www.orcaslicer.com/wiki/cli/cli_transform)
- **[primary]** Chopper (Luo, Baran, Rusinkiewicz, Matusik; ACM TOG 31(6), SIGGRAPH Asia 2012): partitions a model so parts fit the build volume, with criteria "assemblability", few parts, "unobtrusiveness of the seams", "structural soundness"; prototype adds "customized connectors" at interfaces; project page offers paper/video/user study but no code. — [Chopper project page](https://pixl.cs.princeton.edu/pubs/Luo_2012_CPM/index.php); [PDF](https://gfx.cs.princeton.edu/pubs/Luo_2012_CPM/chopper.pdf); related patent US10025882 — [Google Patents](https://patents.google.com/patent/US10025882)
- **[primary]** pychop3d (gregstarr): "Python implementation of 'Chopper: Partitioning Models into 3D-Printable Parts'", MIT, 23 stars, "Must use python 3.7" (Windows note), config keys `beam_width`, `connector_diameter`, `connector_spacing`, `connector_tolerance`, `printer_extents` (no delta printers), `plane_spacing`, `part_separation` (experimental); outputs "the output stls, config file, and save progress"; bunny "about 2 minutes", shoerack "about 45 minutes". Last-commit date not shown on the page; an aggregator lists it as updated about a year earlier (**[secondary]**). — [pychop3d](https://github.com/gregstarr/pychop3d); [ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fgregstarr%2Fpychop3d)
- **[primary]** fogleman/choppy (Go, 36 stars): interactive "Chop 3D models in half with a user-defined slice plane", outputs two STLs; no connectors, license not shown. — [choppy](https://github.com/fogleman/choppy)
- **[older, secondary]** Other partitioning literature without found code: Dapper ("decompose-and-pack", SIGGRAPH Asia 2015; "only makes planar cuts", pyramidal parts); PackMerger (CGF 2014; shells into packable parts); level-set partitioning and packing (SIGGRAPH Asia 2015); "Interactive partitioning of 3D models into printable parts" (NTU/TU Delft; built on Chopper with no-go painting). — [Dapper (SIGGRAPH archive)](https://history.siggraph.org/?p=210366); [PackMerger PDF](https://www.cs.purdue.edu/homes/bbenes/papers/Vanek14CGF.pdf); [Level-set partitioning (SIGGRAPH archive)](https://history.siggraph.org/?p=210390); [Interactive partitioning (TU Delft)](https://research.tudelft.nl/en/publications/interactive-partitioning-of-3d-models-into-printable-parts)
- **[primary]** "Print each color as a separate part then assemble" vs painting: PrusaSlicer's painting "colored 'parts' cannot be exported separately", so separate-part workflows require real per-color geometry; Bambu's wiki shows cutting into "a multi-part object and coloring it" with numeric shortcuts to assign filaments per part. — [Prusa KB painting](https://help.prusa3d.com/article/multi-material-painting_262620); [Bambu Wiki Cut tool](https://wiki.bambulab.com/en/software/bambu-studio/cut-tool)
- **[primary]** Splitting shells: Bambu's "Split to objects/parts" and PrusaSlicer's "Split to objects/parts" separate disconnected shells into objects or parts for per-part filament/settings. — [Bambu Wiki](https://wiki.bambulab.com/en/software/bambu-studio/split-to-objects-parts); [Prusa KB](https://help.prusa3d.com/article/split-to-objects-parts_1751)

### Inferences
- A scriptable equivalent of the slicer cut tool: plane cut with manifold3d `split_by_plane` (robust, manifold-preserving), then subtract cylinders/prisms for dowel holes from both halves and emit a dowel body (PrusaSlicer's "Dowel" semantics), or add a boss on one side and a hole on the other ("Plug"). Apply tolerance as a radial/XY offset on the hole only, matching the "XY hole compensation" interpretation; start around 0.1-0.2 mm radial for press fit and 0.25-0.4 mm for glue/slip fits, then calibrate with a printed gauge (numbers are secondary and printer-dependent).
- Orient each cut part with its cut face down ("Place on cut") when that face is large and flat; this is what both slicers offer and it removes most supports for split organic shapes.
- For multi-plate color workflows on single-nozzle machines, printing each color as a separate part per plate removes flushing entirely at the cost of assembly; this is the waste-optimal path when the design permits mechanical joints.

### Gaps
- No official tolerance recommendation from Prusa or Bambu for cut connectors; behaviour reports conflict.
- No maintained open-source implementation of Dapper, PackMerger or level-set partitioning was found; pychop3d's recency and macOS/arm64 compatibility are unverified.

## Key question 6: Plate packing / arrangement libraries and CLIs

### Takeaway
libnest2d (LGPL-3.0, C++) is the open-source nesting engine behind PrusaSlicer's arrange (its fork repo last pushed May 2024), pynest2d (Ultimaker, LGPL-3.0) wraps it for Python but publishes no wheels, and in practice the slicer CLIs (OrcaSlicer `--arrange`, PrusaSlicer arranges unless `--dont-arrange`) are the simplest deterministic-enough route.

### Cited Findings
- **[primary]** libnest2d: "a library and framework for the 2D bin packaging problem", LGPL-3.0, 445 stars, 141 forks, last push 2024-05-03; dependencies Clipper, NLopt, Boost Geometry (CMake can download Clipper/NLopt with `RP_ENABLE_DOWNLOADING`); "This repository is a continuation of the original project (effectively a fork)" of the PrusaSlicer-internal library, whose placer "is now used in the PrusaSlicer application's arrangement feature"; "still not feature complete". No Python bindings or macOS notes in the README. — [tamasmeszaros/libnest2d](https://github.com/tamasmeszaros/libnest2d)
- **[primary]** pynest2d: "CPython bindings for LibNest2D", LGPL-3.0, 41 stars, last push 2026-06-25; sip-based; Releases/Packages sections empty (no prebuilt wheels found); platform support not stated. — [Ultimaker/pynest2d](https://github.com/Ultimaker/pynest2d)
- **[primary]** OrcaSlicer CLI: `--arrange` (0 disables, 1 forces, other = auto), `--orient`, `--repetitions` (requires a single-plate `--slice i`), `--assemble`, `--allow-multicolor-oneplate` (default on), `--ensure-on-bed`. — [Orca CLI transform](https://www.orcaslicer.com/wiki/cli/cli_transform); [Orca CLI misc](https://www.orcaslicer.com/wiki/cli/cli_misc)
- **[primary]** PrusaSlicer CLI has `--dont-arrange` and `--merge` (older man pages: `--dont-arrange` keeps original XY coordinates; `--merge` arranges and merges into one model); the GUI has an auto-arrange tool; PrusaSlicer's source tree contains a `libseqarrange` module (sequential arrangement). — [prusa-slicer(1) trixie](https://dyn.manpages.debian.org/trixie/prusa-slicer/prusa-slicer.1); [Ubuntu man page](https://manpages.ubuntu.com/manpages/jammy/man1/prusa-slicer.1.html); [Prusa KB: Auto-arrange](https://help.prusa3d.com/article/auto-arrange-tool_1770); [PrusaSlicer src tree](https://github.com/prusa3d/PrusaSlicer/tree/master/src)
- **[primary]** Bambu/Orca plate membership is explicit in `model_settings.config` (`<plate>` + `<model_instance object_id/instance_id/identify_id>`), so a generator can place objects on specific plates without arrangement. — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp)

### Inferences
- For deterministic output, do the layout in Python (e.g., shelf/skyline packing of part bounding boxes or convex hulls with a per-printer margin) and write explicit transforms + plate assignments; use `--arrange 0` when round-tripping through OrcaSlicer so it does not reshuffle plates.
- pynest2d would require a local build (sip + libnest2d + Boost/Clipper/NLopt) on arm64 macOS; not verified.

### Gaps
- No evidence of macOS arm64 build instructions or wheels for pynest2d/libnest2d.

## Key question 7: Practical constraints (bleed, purge towers, flush volumes) as they shape model generation

### Takeaway
Flush volume is driven by color pairs (dark-to-light worst), the prime tower must reach the highest color-change layer, and every extra filament on a layer costs one change; Bambu's own guidance (multiplier 0.8-0.9, flush into infill/support/sacrificial objects, flip parts so changes are low, raise layer height) translates directly into generator heuristics.

### Cited Findings
- **[primary]** Flush multiplier: "a multiplier of 1.00 is the default, with 0.90 being 10% less flushing volume"; "A Multiplier of 0.8 or 0.9 could be a quick way to save filament, but it is important to run test prints"; too low "will show as discolored layers". — [Bambu Wiki: Reduce wasting](https://wiki.bambulab.com/en/software/bambu-studio/reduce-wasting-during-filament-change)
- **[primary]** Flush into infill: usable because infill "is almost always covered by the part's outer shell", but "lighter colors and transparent colors... will allow the oddly colored infill... to show through", worse with few walls. Flush into support is enabled by default but "will not take effect unless the Prime Tower is enabled". "Flush into this object": a colored Bambu Cube "would normally require about 70g of flushed filament" but with sacrificial objects "the flushed filament is instead less than a gram"; flush objects "similar height to the multimaterial parts are ideal". — [Bambu Wiki: Reduce wasting](https://wiki.bambulab.com/en/software/bambu-studio/reduce-wasting-during-filament-change)
- **[primary]** PrusaSlicer: "During a filament change, a small amount of melted plastic remains in the nozzle... PrusaSlicer provides several ways to deposit this filament: Smart wipe tower, Wipe to infill, Wipe to object"; purging volumes set in "Printer Settings -> Single extruder MM setup" or per project. The wipe tower "size is not dependent on the size of the object being printed but on the amount of color changes"; "the ratio of sparse and dense infill is automatically adjusted every layer"; changing the support extruder with non-Organic supports "will disable the wipe tower". — [Prusa KB: Purging volumes (MMU)](https://help.prusa3d.com/article/purging-volumes-mmu_125097); [Prusa KB: Wipe tower](https://help.prusa3d.com/article/wipe-tower_125010)
- **[secondary]** Third-party claims of a ~280 mm3 default flush and "153 filament changes and 83g of wasted filament" for a 4-color cube at 0.2 mm were attributed to the Bambu wiki but not found on the fetched page (**[unverified]**). — [evezone purge tuning](https://evezone.evetech.co.za/build-lab/how-to-print-multi-colour-with-the-ams-swaps-purge-and-flush-tuning)
- **[primary]** Color sequence per layer is controllable in the project: Bambu's plate metadata carries `first_layer_print_sequence`, `other_layers_print_sequence`, `filament_map_mode`, `filament_map` (multi-nozzle mapping). — [OrcaSlicer bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp)

### Inferences
- Generator heuristics: (1) minimize distinct filaments per layer and total changes (sum over layers of filaments-1); (2) put color detail low in Z or orient the part so changes cluster near the bed; (3) avoid light/transparent filaments as the "to" color after dark ones at boundaries you care about; (4) when exporting Bambu projects, optionally add sacrificial "flush into this object" bodies of similar height; (5) use thicker layers in color-only regions where surface quality allows.
- Color bleed at interfaces is a slicer/printer tuning matter (flush volumes), not a model matter, except that very small regions are disproportionately affected and should be merged (see Key question 4).

### Gaps
- Exact default flush volumes (mm3) and Bambu's flush algorithm constants were not on the fetched wiki page; they live in the slicer's filament profiles/source and were not extracted.
- Prusa's default purging volume numbers were not captured (page text truncated before the values).

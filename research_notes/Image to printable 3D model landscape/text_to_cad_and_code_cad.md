## Q1. What exactly is `earthtojake/text-to-cad`?

### Takeaway
`earthtojake/text-to-cad` is a very large (25.8k stars), MIT-licensed, actively released (several releases per day in early Nov 2026) **agent plugin / skill library plus a local Python server**, created 2026-04-22. The agent (Claude Code, Codex, Cursor, etc.) writes **build123d Python scripts** decorated with `@model`; a warm local server built on **OpenCASCADE via `cadquery-ocp-novtk` 8.x** executes them and exports STEP/STL/3MF/GLB/DXF. It does **not** wrap the Zoo API and does not use OpenSCAD or CadQuery. It is entirely code-based and deterministic in the sense this repository wants, but its own docs catalogue OCCT fillet/boolean/loft failure modes and the project has shipped (and fixed) at least one non-manifold STL export bug.

### Inferences
- For the target pipeline, the most reusable parts of this repo are not the agent plugin but its **conventions**: build123d script per part, OCCT-rendered snapshots for the agent, measurement "check scripts" instead of visual judgement, explicit mesh tolerance for printable exports, and its written catalogue of OCCT failure modes. These are all primary-source documented and MIT.
- The dependency on **Python 3.14 and OCP 8.0.x** (via `cadquery-ocp-novtk`) means it tracks the bleeding edge of the OCCT wheel stack; the issue tracker shows it carries workarounds for OCCT/OCP bugs, which is a maintenance-risk signal for anyone vendoring its code rather than its ideas.
- Watertightness is **not** automatically guaranteed by B-rep: issue #433 shows that the tessellation step (B-rep → STL) can still produce non-manifold meshes; a post-export mesh check remains necessary.

## Q2. Zoo (formerly KittyCAD) Text-to-CAD, KCL, API, pricing, SDK, terms

### Takeaway
As of Nov 2026 the original REST endpoint `POST /ai/text-to-cad/{output_format}` is **no longer in Zoo's public OpenAPI spec, Python SDK (kittycad 1.10.0), or CLI**; text-to-CAD now runs through the **Zookeeper agent websocket (`/ws/ml/copilot`)**, which "ONLY" returns **KCL**, and geometry/export requires Zoo's **proprietary, cloud-only engine** (via `zoo kcl export` or the Engine API). KCL is open source (MIT, Rust, in `modeling-app`), the engine is not. Pricing is usage-based by the second ($0.50/min as of the Sept 2025 blog; current numbers are rendered client-side and could not be scraped). Terms (Apr 2026) give users ownership of Outputs but allow Zoo to train on customer materials unless your tier allows opt-out. This is a closed, networked dependency, so it is a poor fit for a deterministic local pipeline, though its design philosophy (parametric B-rep, not meshes) matches.

### Inferences
- A pipeline that calls Zoo must now implement a **websocket agent loop** (prompt → KCL) **plus** a second cloud call to execute/export KCL (CLI `zoo kcl export` or Engine API). There is no local KCL execution path because geometry is computed by the closed engine; the open-source `kcl-lib` is a parser/interpreter front-end whose geometry commands go to the engine.
- The retirement of the single-shot REST endpoint and the "it might not even compile" reasoning messages indicate Zoo itself moved to an iterative agent-with-feedback design rather than one-shot generation.
- Terms: "internal business purposes" plus training-on-customer-materials-by-default make Zoo a questionable dependency for an open pipeline whose outputs might be redistributed.

- Current plan prices and included minutes (Nov 2026) could not be verified; only the Sept 2025 blog numbers are concrete.

- No independent accuracy benchmark of Zookeeper (Text2CAD-Bench et al. do not include it).
- Whether Zoo's engine export is watertight for FDM was not evaluated by any source found.

## Q3. Open-source code-CAD kernels usable from Python

### Takeaway
On Apple Silicon in Nov 2026, **build123d 0.13.0 and CadQuery 2.8.0 install with plain `pip` via `cadquery-ocp` 8.0.1.1.0 wheels (macosx_11_0_arm64, CPython 3.11–3.14)**, both Apache-2.0 on OCCT 8.0.1; build123d's `Mesher` is the only one of the two with documented multi-part, per-colour 3MF export. **OpenSCAD's stable release is still 2021.01 (Intel-only on macOS), but a 2026 release is imminent: tag `openscad-2026.11-RC0` (2026-10-31), release-candidate Universal (Intel + Apple Silicon) dmg on the download page, Manifold as default backend (merged 2025-08-17), and colour export to 3MF; Homebrew ships `openscad@snapshot` 2026.10.11.** pythonocc-core 8.0.1.2 is conda-only (osx-arm64 available). FreeCAD 1.1.4 ships a native arm64 dmg. Blender's `bpy` 5.2.3 has an arm64 wheel but lacks native 3MF export.

## Q4. LLM-generated CAD code: research, benchmarks, failure modes, deterministic verification

### Takeaway
2025–2026 research converged on **generating executable CAD code (overwhelmingly CadQuery Python)** rather than DeepCAD-style command vectors, because code can be executed and checked. Frontier models are reasonable on simple sketch-extrude parts (Text2CAD-Bench L1 invalidity ~11–20%) but **collapse on sweep/loft/shell (L3 invalidity 70–90%)**, and executability is largely independent of geometric correctness. Verification has shifted to deterministic, kernel-level checks: execution in a sandbox, B-rep validity, Chamfer/IoU against ground truth, executable "CADTests", DFM checks and even FEA, with VLM render-and-compare as a weaker complement.

### Cited Findings
**Benchmarks and datasets**
- (older) DeepCAD (2021-05-20): "the first 3D generative model" for shapes as "a sequence of computer-aided design (CAD) operations" [primary] — [arXiv 2105.09492](https://arxiv.org/abs/2105.09492); Fusion 360 Gallery (2020-10-05): "a dataset of 8,625 human design sequences" in a sketch+extrude language [primary] — [arXiv 2010.02392](https://arxiv.org/abs/2010.02392)
- (older) Text2CAD (2024-09-25, NeurIPS'24 spotlight): ~170K DeepCAD models with ~660K text annotations generated with Mistral and LLaVA-NeXT; transformer autoregressive; repo 493 stars, last push 2025-05-15, licence not asserted [primary] — [arXiv 2409.17106](https://arxiv.org/abs/2409.17106), [SadilKhan/Text2CAD](https://github.com/SadilKhan/Text2CAD)
- (older) CADCodeVerify / **CADPrompt** (v2 2025-02-28): CADPrompt = "200 natural language prompts" with expert code; VLM generates and answers validation questions; on GPT-4 "7.30% reduction in Point Cloud distance" and "5.0% improvement in success rate" [primary] — [arXiv 2410.05340](https://arxiv.org/abs/2410.05340)
- **Text2CAD-Bench** (2026-05-18): 600 human-curated examples (L1 200, L2 200, L3 100, L4 100), 1,200 prompts (geometric vs sequence style); target representation **CadQuery**; metrics Chamfer Distance (×10³), Invalidity Rate (execution failure, 60 s timeout, empty/degenerate geometry), IoU at 256³, GLM-4.6V judge for L4; up to 3 retries with error feedback. Headline (geometric prompts): GPT-5.2 L1 CD 44.31 / IR 11.1% / IoU 0.59 but L3 IR 68.0%; Claude-4.5-Sonnet L1 IR 20.3%, L3 IR 70.0%; Gemini-3-Flash L3 IR 12.8% but IoU 0.20; fine-tuned Text2CAD L1 IR 11.0% with IoU 0.08 ("syntactically valid but geometrically imprecise"); CADFusion L1 IR 60%; Text2CADQuery L3 IR 80%. "Advanced operations (sweep, loft, shell)" make IR reach 70–90%; DeepCAD-style command sequences (run via PythonOCC) worsened invalidity vs CadQuery; limits: single bodies only, no assemblies [primary] — [arXiv 2605.18430](https://arxiv.org/abs/2605.18430)
- **BenchCAD** (2026-05-11): "17,900 execution-verified CadQuery programs across 106 industrial part families, including bevel gears, compression springs, twist drills"; tasks VQA, code QA, image-to-code, instruction-guided code editing [primary] — [arXiv 2605.10865](https://arxiv.org/abs/2605.10865)
- **CADTests / CADTestBench** (2026-05-08): "executable software tests that verify whether a generated CAD model satisfies the geometric and topological requirements of the input prompt"; "CADTests can also guide CAD model generation, yielding simple baselines that surpass performance of current methods" [primary] — [arXiv 2605.07807](https://arxiv.org/abs/2605.07807)
- **CADEngBench** (2026-08-10): 300 parametric parts × (zero-to-CAD + functional edit) = 600 tasks, evaluated via "B-Rep validity, engineering and DFM checks, parameter-family perturbations, functional editing, and matched linear-static FEA in CalculiX"; plus 150 assembly body pairs; "Across eight multimodal, code-capable models, editing supplied CAD is substantially easier than generating it" [primary] — [arXiv 2608.09296](https://arxiv.org/abs/2608.09296)
- **CADGenBench** (Hugging Face): tasks = generate a part from an engineering drawing, or edit a STEP to a requested change; tool-agnostic ("build123d, Autodesk Fusion, Onshape"); submission is one STEP/BREP per sample; scored server-side against private ground truth; Apache-2.0; reference baseline "iteratively writes CAD code, validates the artifact, and repeats until valid" with build123d and CadQuery backends [primary] — [huggingface/cadgenbench](https://github.com/huggingface/cadgenbench), [leaderboard Space](https://huggingface.co/spaces/HuggingAI4Engineering/CADGenBench). Third-party leaderboard snapshots conflict (e.g., a build123d agent on Claude Opus 5 at 59.6% on 2026-08-12; "Godela" 84.5% on 2026-09-23; an early GPT-5.5 Pro baseline at 0.387) and mix agents/tools, so they are not clean model comparisons [secondary, conflicting] — [benchlm](https://benchlm.ai/benchmarks/cadgenbenchgeneration), [llm-stats](https://llm-stats.com/benchmarks/cadgenbench)

**Methods (text → code)**
- Text-to-CadQuery (2025-05-10): "generating CadQuery code directly from text, leveraging the strengths of pretrained LLMs ... without intermediate representations"; a search snippet reports best top-1 exact match 69.3% after fine-tuning and that most open-source models failed to produce valid CadQuery while commercial ones could [primary abstract; numbers secondary] — [arXiv 2505.06507](https://arxiv.org/abs/2505.06507)
- **ReliCAD** (2026-09-16): names "a fundamental contradiction ... between their probabilistic generation and the deterministic requirements of CAD modeling"; converts requirements into structured design specifications with explicit geometric relations, topological dependencies and feature order, then "invokes the CAD kernel through an Agent-ready API" [primary] — [arXiv 2609.22325](https://arxiv.org/abs/2609.22325)
- (older) CAD-Assistant (2024-12-18): VLLM planner issuing actions "iteratively executed on a Python interpreter equipped with the FreeCAD software", with tools including "a sketch image parameterizer, rendering modules, a 2D cross-section generator" [primary] — [arXiv 2412.13810](https://arxiv.org/abs/2412.13810)
- (older) CAD-MLLM (2024-11-07, Omni-CAD dataset, command sequences) and OpenECAD (2024-06-14, VLMs 0.55B–3.1B) are command-sequence approaches [primary] — [arXiv 2411.04954](https://arxiv.org/abs/2411.04954), [arXiv 2406.09913](https://arxiv.org/abs/2406.09913)
- **MIRAGE-CAD** (2026-08-24): four input types (text, rendered image, point cloud, STEP/B-rep) mapped to a construction plan; Python CAD code "executed by an OpenCASCADE kernel to build the solid and export it as STEP"; "55.4–70.0% build success and 52.3–66.2% STEP export success" on 2,500 held-out queries per modality [primary] — [arXiv 2608.28669](https://arxiv.org/abs/2608.28669)
- **VisCAD** (2026-09-03): a 27B model (VisCAD-M1) for "renders, text descriptions, 2D drawings, and real photographs" → "executable programs in a CAD domain-specific language"; benchmarks PubCADBench and RealCADBench [primary] — [arXiv 2609.03811](https://arxiv.org/abs/2609.03811)

**Tooling: MCP servers / agent harnesses**
- `pzfreo/build123d-mcp`: "MCP server for build123d to improve AI cognition when creating 3D CAD models", Apache-2.0, 144 stars, pushed 2026-10-15; on PyPI as `build123d-mcp` [primary metadata]; its README reportedly claims a CADGenBench score lift from 0.360 to 0.457 for the same model (June 2026) [secondary] — [build123d-mcp](https://github.com/pzfreo/build123d-mcp), [PyPI](https://pypi.org/project/build123d-mcp/)
- `CadQuery/cadquery-contrib` (MIT, 77 stars, pushed 2026-10-20) hosts `cadquery-mcp` 0.1.0 whose listed tool executes CadQuery and returns SVG renders [primary metadata; feature list secondary] — [cadquery-contrib](https://github.com/CadQuery/cadquery-contrib), [PyPI cadquery-mcp](https://pypi.org/project/cadquery-mcp/)
- OpenSCAD MCP servers exist but none is canonical: `quellant/openscad-mcp` (FastMCP, `OPENSCAD_PATH`, `MCP_RENDER_TIMEOUT`), `rahulgarg123/openscad-mcp` (Node, renders PNG), `jhacksman/OpenSCAD-MCP-Server`, PyPI `openscad-mcp-server` ("14 tools") [secondary, unverified] — [quellant/openscad-mcp](https://github.com/quellant/openscad-mcp), [PyPI openscad-mcp-server](https://pypi.org/project/openscad-mcp-server/)
- BlenderMCP: `ahujasid/blender-mcp` redirects to **`ahujasid/mcp-for-blender`**, 33,672 stars, MIT, pushed 2026-11-04, "Community plugin to control Blender 3D with any LLM" (mesh/scene tool, not parametric CAD) [primary] — [mcp-for-blender](https://github.com/ahujasid/mcp-for-blender)
- Zoo's own agent exposes reasoning types `generated_kcl_code` ("might not even compile") and `kcl_code_error`, i.e., an execute-and-repair loop [primary] — [api.zoo.dev](https://api.zoo.dev/)

**Failure modes (documented)**
- Execution failures (syntax/runtime), timeouts, empty or degenerate geometry; sharp drop on sweep/loft/shell; "Low IR does not guarantee accuracy"; survivorship bias in CD/IoU when IR is high [primary] — [Text2CAD-Bench](https://arxiv.org/abs/2605.18430)
- Hallucinated API methods, wrong argument order, calling methods on the wrong object type for CadQuery/build123d; OpenSCAD's "small, stable language gives fewer chances to go wrong" [secondary] — [GrandpaCAD](https://grandpacad.com/en/blog/openscad-vs-cadquery-vs-build123d)
- Kernel-level: fillets silently skipping edges, fillet crashes on tangent chains, Booleans "returning successfully" with bad geometry near tangency, lofts joining mis-oriented sections, Boolean that removes everything → empty Compound; tessellation producing zero-area/duplicate triangles at hole/curved-face intersections [primary, project docs/issues] — [build123d-modeling.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/build123d-modeling.md), [Issue #433](https://github.com/earthtojake/text-to-cad/issues/433)
- Spatial reasoning and under-specified prompts (hole positions missing) per practitioners [secondary] — [HN 47970497](https://news.ycombinator.com/item?id=47970497)

**Deterministic verification patterns in use**
- Execute in a sandbox with timeout and classify invalid outputs (Text2CAD-Bench, 60 s) [primary] — [arXiv 2605.18430](https://arxiv.org/abs/2605.18430)
- Executable unit tests over geometry/topology (CADTests) [primary] — [arXiv 2605.07807](https://arxiv.org/abs/2605.07807)
- B-rep validity + DFM rules + parameter perturbation + FEA (CADEngBench) [primary] — [arXiv 2608.09296](https://arxiv.org/abs/2608.09296)
- Measurement scripts rather than pictures; OCCT-rendered snapshots only for arrangement ("A number is never read off a picture") [primary] — [SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/SKILL.md)
- Mesh-level: build123d `Mesher` warns on non-manifold output; the text-to-cad project's `dfam-check` reports `watertight`; Bambu Studio's manifold flag used as an external oracle [primary] — [import_export](https://build123d.readthedocs.io/en/latest/import_export.html), [Issue #433](https://github.com/earthtojake/text-to-cad/issues/433)
- Render-and-compare with a VLM (CADCodeVerify; Text2CAD-Bench L4 judge) as a complement; rendered meshes fed back for iterative refinement (CADReasoner, CADENA) [primary] — [arXiv 2410.05340](https://arxiv.org/abs/2410.05340), [arXiv 2603.29847](https://arxiv.org/abs/2603.29847), [arXiv 2608.00799](https://arxiv.org/abs/2608.00799)

### Inferences
- The field's own metric choices (execution validity, B-rep validity, CD/IoU, CADTests) validate the repository's preference for deterministic code-CAD: every serious 2026 benchmark scores by **executing** the generated program on a kernel, not by judging a mesh.
- A practical pipeline should expect to need **retry-with-error-feedback** (used by Text2CAD-Bench and CADGenBench's baseline) and should budget for high failure rates whenever sweep/loft/shell or fillets are required; favour primitives, extrusions, revolves, holes, patterns, and explicit chamfers where possible.
- The GrandpaCAD result (OpenSCAD fewer code errors than build123d with a cheap model) and the research result (CadQuery B-rep executes/scores better than command sequences) are not contradictory: OpenSCAD is easier for a model to write, B-rep kernels are more capable; the choice depends on model strength and feature needs.

### Gaps
- No paper benchmarks **OpenSCAD** code generation head-to-head with CadQuery/build123d; the only comparison is the GrandpaCAD blog (secondary, undated, one cheap model).
- No benchmark measures **printability** (watertightness, min wall thickness, overhangs) of LLM-generated parts; CADEngBench's DFM checks are the closest.
- Precise numbers for CAD-Recode, cadrille, CAD-Coder beyond their abstracts were not extracted; Text-to-CadQuery's 69.3% is from a search snippet.
- Whether any of the open research models run on Apple Silicon (MPS) was not documented anywhere found; CAD-Recode is Qwen2-1.5B-based (small) but its repo gives CUDA-oriented instructions and a ZeroGPU demo.

## Q5. Image / sketch-to-CAD (reverse engineering a photo or drawing into a parametric model)

### Takeaway
Image-to-parametric-CAD is an active 2024–2026 research area with usable open models for **clean renders and point clouds** (CAD-Recode, cadrille, CAD-Coder, CADENA, CADReasoner) and growing attention to **real photos and hand sketches** (Img2CAD, VisCAD, Composable CAD, Zoo's Zookeeper uploads), but reported build-success rates for realistic inputs are ~55–70% at best and none of the research systems is packaged as a Mac-friendly CLI. The maturity is "research prototype", with a strong trend toward iterative, execution-grounded refinement rather than single-pass prediction.

### Cited Findings
- (older) **Img2CAD** (2024-07-19; search listing says SIGGRAPH Asia 2025): factorises image → "global discrete base structure" via a fine-tuned Llama3.2 VLM, then a "TrAssembler" predicts continuous attributes; motivates with "photometric variability and sensor noise" [primary] — [arXiv 2408.01437](https://arxiv.org/abs/2408.01437)
- (older) **GenCAD** (2024-09-08): image-conditioned autoregressive transformer + contrastive learning + latent diffusion → parametric CAD command sequences [primary] — [arXiv 2409.16294](https://arxiv.org/abs/2409.16294)
- **CAD-Recode** (2024-12-18, ICCV 2025): point cloud → CadQuery Python; "trained upon Qwen2-1.5B, keeping original tokenizer, and adding a single additional linear layer"; trained on 1M procedurally generated sequences; repo 278 stars, last push 2025-11-16, Hugging Face weights v1/v1.5 and a ZeroGPU Space [primary] — [filaPro/cad-recode](https://github.com/filaPro/cad-recode), [arXiv 2412.14042](https://arxiv.org/abs/2412.14042)
- **cadrille** (2025-05-28): one VLM for point clouds, images and text; SFT on procedural data then RL (GRPO) "using online feedback, obtained programatically" [primary] — [arXiv 2505.22914](https://arxiv.org/abs/2505.22914)
- **CAD-Coder** (2025-05-20): open-source VLM fine-tuned to emit CadQuery from images; GenCAD-Code dataset of 163k image/code pairs; "100% valid syntax rate", beats GPT-4.5 and Qwen2.5-VL-72B on solid similarity; "some signs of generalizability" to real images [primary] — [arXiv 2505.14646](https://arxiv.org/abs/2505.14646)
- **CADReasoner** (2026-02-18): iteratively refines a CadQuery program using "geometric discrepancy between the input and the predicted shape"; fuses multi-view renders and point clouds; scan-simulation to bridge the realism gap; evaluated on DeepCAD, Fusion 360, MCB [primary] — [arXiv 2603.29847](https://arxiv.org/abs/2603.29847)
- **CADENA** (2026-08-01): grows the CAD program one operation at a time, "comparing the target with the currently predicted geometry at every step"; introduces CADENA-Bench of mechanical parts; code at github.com/zhemdi/cadena [primary] — [arXiv 2608.00799](https://arxiv.org/abs/2608.00799)
- **Img2CADSeq** (2026-05-13): single image → coarse-to-fine point cloud → VQ-diffusion over a 3-level hierarchical codebook of CAD operations; new CAD-220K and PrintCAD datasets; outputs "standard STEP files" [primary] — [arXiv 2605.13293](https://arxiv.org/abs/2605.13293)
- **DIP-CAD** ("A Design-Intent-Preserving Agent Harness for Parametric CAD Modeling", 2026-09-19; listed in search as Vision2CAD): VLM + CAD-kernel operations to establish "ID-based explicit geometry reference" and sketch constraints so edits preserve design intent, from images [primary] — [arXiv 2609.22688](https://arxiv.org/abs/2609.22688)
- **MIRAGE-CAD** and **VisCAD** (see Q4) also accept images/photos/drawings; MIRAGE reports 55.4–70.0% build success per modality [primary] — [arXiv 2608.28669](https://arxiv.org/abs/2608.28669), [arXiv 2609.03811](https://arxiv.org/abs/2609.03811)
- **BenchCAD** includes an image-to-code task over 17,900 CadQuery programs; **CADGenBench** scores drawing-to-STEP generation [primary] — [arXiv 2605.10865](https://arxiv.org/abs/2605.10865), [cadgenbench](https://github.com/huggingface/cadgenbench)
- Hand-drawn sketches: **Composable CAD** (2026-10-31) uses off-the-shelf VLMs to synthesise part-wise CAD programs from a sketch, recovers constraints into a "coarse proxy", and applies "a deterministic rewrite to ensure that neighboring components meet"; earlier sketch-parameterisation work: PICASSO (2024-07-18), CadVLM (2024-09-26), Sketch2CAD (2023-09-28), Vitruvion (2021-09-29) [primary titles/abstracts via arXiv API] — [arXiv 2611.01165](https://arxiv.org/abs/2611.01165), [arXiv 2407.13394](https://arxiv.org/abs/2407.13394), [arXiv 2409.17457](https://arxiv.org/abs/2409.17457), [arXiv 2309.16850](https://arxiv.org/abs/2309.16850), [arXiv 2109.14124](https://arxiv.org/abs/2109.14124)
- Commercial: Zoo's Zookeeper accepts "photos of hand sketches", PDF/DXF drawings and STEP since March 2026, outputting KCL; no accuracy figures published [primary] — [March 2026 post](https://zoo.dev/blog/whats-new-mar-2026)

### Inferences
- For the target pipeline (photo/description → printable part), the research consensus is a **two-stage** approach: a VLM proposes structure/parameters, a deterministic kernel builds it, and discrepancy feedback (renders, point clouds, measurements) drives revision. This maps directly onto a code-CAD loop with build123d/OpenSCAD and does not require mesh-generation AI.
- Open models that emit CadQuery (CAD-Recode, cadrille, CAD-Coder) are the most directly reusable artefacts, but they are trained on synthetic sketch-extrude distributions; their outputs on consumer-object photos are unproven.

### Gaps
- No source quantifies performance on **real photographs of everyday printable objects** (as opposed to renders of DeepCAD-style parts) except VisCAD's "real photographs" claim, whose numbers were not extracted.
- No Apple-Silicon/MPS inference reports for any of these models; VisCAD-M1 at 27B is out of reach for a 16 GB machine without quantisation (inference, not cited).
- Web-search budget was exhausted before community sketch-to-CAD tools (e.g., slicer-vendor features) could be surveyed.

## Q6. Deterministic parametric libraries for common printable features

### Takeaway
The deepest, print-aware deterministic library is **BOSL2 for OpenSCAD** (BSD-2-Clause, releases daily, `$slop`-aware joiners, snap pins, rabbit clips, dovetails, knuckle and living hinges, threads, screws, bottle caps, gears). On the Python side, **bd_warehouse** (build123d, Apache-2.0, 0.4.0 Oct 2026) covers threads, fasteners, bearings, gears, pipes, O-rings, keys and sprockets, and build123d/OpenSCAD both have native text objects for embossing. No Python-side snap-fit/tolerance helper or keychain-loop library was found.

### Cited Findings
- **BOSL2**: 2,453 stars, 216 forks, 27 open issues, **BSD-2-Clause**, pushed 2026-11-08; latest release **v2.0.785 (2026-11-08)**; README: "Requires OpenSCAD 2021.01 or later" and "BOSL2 IS BETA CODE" [primary] — [BelfrySCAD/BOSL2](https://github.com/BelfrySCAD/BOSL2)
- BOSL2 file list: basic (constants, transforms, attachments, shapes2d/3d, masks, drawing, distributors, color, partitions), advanced (paths, regions, skin, vnf, beziers, nurbs, rounding, turtle3d, isosurface), threaded parts (**threading, screws, screw_drive, bottlecaps**), parts (ball_bearings, cubetruss, **gears, hinges, joiners**, linear_bearings, modular_hose, nema_steppers, polyhedra, sliders, tripod_mounts, walls, wiring, **hooks**); threading provides "generic threading" and "specific threading to match plastic bottles, pipe fittings, or standard screws"; a third-party "Attachable Text3d" library is linked for text [primary] — [BOSL2 wiki](https://github.com/BelfrySCAD/BOSL2/wiki)

### Inferences
- If the pipeline's agent targets OpenSCAD, BOSL2 gives print-tolerance-aware snap/hinge/thread primitives for free and is permissively licensed; NopSCADlib is richer in "vitamins" but GPL-3.0.
- If it targets build123d, bd_warehouse covers threads/fasteners/gears but **snap-fits, clips, living hinges and keychain loops would have to be written as in-house helpers**.

### Gaps
- No Python library for snap-fit/clearance helpers or keychain loops was found (web search exhausted before a dedicated search).
- BOSL2's compatibility with the 2026 OpenSCAD RC was not checked beyond "2021.01 or later".
- NopSCADlib's detailed module list and OpenSCAD version requirement were not visible on the fetched page.

## Q7. Practical: headless OpenSCAD and CadQuery/build123d on macOS arm64; 3MF with multiple bodies/colours

### Takeaway
Yes on both counts, with caveats. **build123d/CadQuery**: `pip install build123d` (or `cadquery`) on CPython 3.11–3.14 pulls arm64 `cadquery-ocp` wheels; build123d's `Mesher` writes multi-part 3MF with per-part colour and label and warns on non-manifold meshes; CadQuery's 3MF writer has no colour. **OpenSCAD**: use the Universal RC/snapshot (`brew install --cask openscad@snapshot`, 2026.10.11) and drive the binary from Python; `--backend=manifold` and `-O export-3mf/color-mode=model` (plus `unit`, `material-type`) control the 3MF; the stable 2021.01 is Intel-only, CGAL-only and colour-blind. Slicer interoperability of coloured 3MF from OpenSCAD is still reported as inconsistent in community posts.

### Cited Findings
- `cadquery-ocp` 8.0.1.1.0 ships `macosx_11_0_arm64` wheels for cp311–cp314 [primary] — [PyPI cadquery-ocp](https://pypi.org/project/cadquery-ocp/); build123d 0.13.0 requires Python >=3.11,<3.15 and installs with `pip install build123d` [primary] — [PyPI build123d](https://pypi.org/project/build123d/), [installation](https://build123d.readthedocs.io/en/latest/installation.html); CadQuery 2.8.0 requires >=3.11 and documents `pip install cadquery` (conda "better supported") [primary] — [PyPI cadquery](https://pypi.org/project/cadquery/), [README](https://github.com/CadQuery/cadquery/blob/master/README.md)
- The `cad` package from earthtojake/text-to-cad runs this exact stack headless on macOS (installer fetches Python 3.14 through uv; `cadquery-ocp-novtk` variant without VTK) [primary] — [docs/install.md](https://github.com/earthtojake/text-to-cad/blob/main/docs/install.md), [PyPI cad](https://pypi.org/project/cad/)
- build123d multi-body/colour 3MF: `Mesher().add_shape(...)` per part; colours and labels round-trip; `write("x.3mf")`; non-manifold warning [primary] — [import_export](https://build123d.readthedocs.io/en/latest/import_export.html). CadQuery: "parameters for color and material are absent" for 3MF; writer emits plain `<object>`s [primary] — [importexport](https://cadquery.readthedocs.io/en/latest/importexport.html), [threemf.py](https://github.com/CadQuery/cadquery/blob/master/cadquery/occ_impl/exporters/threemf.py)
- OpenSCAD macOS binaries: stable "64-bit Intel" only; RC and snapshots "64-bit Universal ... supporting Intel and Apple Silicon"; Homebrew `openscad@snapshot` 2026.10.11 (macOS >= 12) [primary] — [downloads](https://openscad.org/downloads.html), [brew](https://formulae.brew.sh/cask/openscad@snapshot)
- OpenSCAD CLI knobs: `--backend` flag "to enable manifold in prod builds #5235" and README build notes referencing `--backend=manifold`; 3MF export options `export-3mf/color-mode={model|none|selected-only}`, `export-3mf/unit={micron|millimeter|centimeter|meter|inch|foot}`, `export-3mf/material-type={color|basematerial}`, `export-3mf/color`, `export-3mf/decimal-precision`, metadata fields, settable from the command line (`-O`) [primary] — [releases/next.md](https://github.com/openscad/openscad/blob/master/releases/next.md), [Settings.cc](https://github.com/openscad/openscad/blob/master/src/core/Settings.cc), [export.h](https://github.com/openscad/openscad/blob/master/src/io/export.h); (older) 2021.01 added `--export-format`, multi-export and STDOUT export [primary] — [RELEASE_NOTES.md](https://github.com/openscad/openscad/blob/master/RELEASE_NOTES.md)
- Multiple objects in an OpenSCAD 3MF depend on the experimental lazy-union feature (top-level items become separate objects) [secondary] — [ModelRift](https://modelrift.com/blog/multicolor-3mf-export/); slicers differ: PrusaSlicer material assignment "depends on the 3MF having multiple defined parts, not on the colors"; Bambu Studio and PrusaSlicer add proprietary colour data beyond the core spec [secondary, mailing-list summaries] — [Hackaday](https://hackaday.com/2025/10/14/openscad-in-living-color), [Bambu forum](https://forum.bambulab.com/t/export-multicolor-design-from-openscad/232511)
- Alternative Python mesh kernel: `manifold3d` 3.5.4 arm64 wheels (Apache-2.0) for robust booleans on meshes [primary] — [PyPI manifold3d](https://pypi.org/project/manifold3d/)
- FreeCAD 1.1.4 native arm64 dmg exists [primary] — [releases](https://github.com/FreeCAD/FreeCAD/releases/latest); Blender `bpy` 5.2.3 arm64 wheel (GPL-3.0, Python 3.13 only) but 3MF needs a GPL add-on without extension/colour support [primary] — [PyPI bpy](https://pypi.org/project/bpy/), [Blender3mfFormat](https://github.com/Ghostkeeper/Blender3mfFormat)

### Inferences
- For a Python CLI on an M5 Mac, the lowest-friction deterministic stack is **build123d + cadquery-ocp (pip) for B-rep → `Mesher` for coloured multi-part 3MF, plus OpenSCAD snapshot/RC as a subprocess when BOSL2 primitives are wanted**, with `manifold3d`/`trimesh` for post-export mesh validation.
- Colour in 3MF is kernel-exportable from both build123d and OpenSCAD, but slicer ingestion (Bambu/Prusa/Orca) must be tested empirically; the sources describe per-object vs per-triangle colour semantics as the main interoperability issue.

### Gaps
- No source addresses memory use of OCCT/build123d or OpenSCAD-Manifold on a **16 GB** machine; nothing suggests it is a problem for single parts, but it is unverified.
- The exact `-O` CLI syntax was confirmed from source, not from the manpage or `--help-export` output (the mailing-list page failed DNS); the RC's actual `--help-export` output should be checked locally.
- FreeCAD headless (`FreeCADCmd`) docs were not reachable this session.
- Community forum sentiment (OpenSCAD forum, r/openscad, CadQuery Discord) could not be surveyed after the search budget ran out.

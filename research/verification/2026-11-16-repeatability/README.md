# Repeatability baseline, 2026-11-16

Restructure plan (`docs/plans/2026-11-16-restructure.md`), Task 0. The question: if we
run today's pipeline twice on the same inputs, which output files come out byte for
byte the same, and which fields of the JSON records change?

The answer sets the comparison for the rebuild proof (Task 9). That proof may ignore
the fields in the table below, and no others.

## Result

**159 output files. 119 are byte-identical. 40 differ.** All 40 differences have one
cause: **the slicers write the time of slicing into the G-code.**

- Each OrcaSlicer G-code differs only in line 2:
  `; generated by OrcaSlicer 2.5.0 on 2026-11-16 at 15:11:34` (local time).
- Each PrusaSlicer G-code (`prusaslicer.portability-only.gcode.txt`, and its `.failed`
  form) differs only in line 1: `; generated by PrusaSlicer 2.9.7 on 2026-11-16 at
  20:11:42 UTC`.
- Every other line of every G-code is the same (for example, 1 of 27136 lines differs
  in the Roadie R1 G-code). The script checks this for each of the 33 differing G-code
  files (`timestamp_only` in the report): all 33 pass.
- The records that hold the hashes of those G-code files (`slice.json`, `strip.json`)
  then differ in those hash fields, and only there.

**Byte-identical in both runs** (by stage):

- `tdmg select`: `selection.json`, `mask.png`, `cutout.png`, `preview.png`.
  Both `selection.json` files are also byte-identical to the originals in
  `artifacts/selection-runs/` (the SHA-256 that `colors.json` records).
- `tdmg flat`: `model.stl`, `outline.png`, `flat.json`.
- `tdmg colors`: `colors.json`, `labels.png`, `regions.png`.
- `tdmg flat --colors`: every STL, `model.3mf`, `palette.json`, `top.png`, `parts.png`,
  `colored.json`.
- `tdmg slice`: `orca-input.3mf`, `plate_1.statistics.json`, `filaments/*.json`.
  In `slice.json`, `slice_id` and `colorslice_id` are the same, and so is each G-code's
  `normalised_sha256` (the hash with the timestamp line taken out).
- `tdmg strip`: the STLs, `skin/model.3mf`, `palette.json`, `results-template.md`,
  statistics and filament files. In `strip.json`, `strip_id` and `geometry_id` are the

- The command output of every step is the same, once the run folder name is replaced.

## The G-code allowance

The G-code files are compared byte for byte, except for one line. That line may differ
only if it matches the pattern in both runs. The patterns are Python regular
expressions, matched against the whole line (`re.fullmatch`, line end removed):

| Slicer | Line | Pattern |
|---|---|---|
| OrcaSlicer 2.5.0 (`plate_1.gcode`, and with `.failed`) | 2 | `; generated by OrcaSlicer 2\.5\.0 on \d{4}-\d{2}-\d{2} at \d{2}:\d{2}:\d{2}` |
| PrusaSlicer 2.9.7 (`prusaslicer.portability-only.gcode.txt`, and with `.failed`) | 1 | `; generated by PrusaSlicer 2\.9\.7 on \d{4}-\d{2}-\d{2} at \d{2}:\d{2}:\d{2} UTC` |

Every other line must match byte for byte, and the line counts must be equal. The
patterns are `ORCA_TIMESTAMP` and `PRUSA_TIMESTAMP` in `scripts/repeat_runs.py`. All 33
differing G-code files pass this check (`timestamp_only: true` in `report.json`).

Why this rule, and not tdmg's `normalised_sha256`: the data supports both. tdmg's
`normalised_sha256` was also equal in all 33 files (`normalised_equal: true`). But
tdmg's patterns are looser than what was measured. `tdmg.slicer` blanks the first
`; generated by ... at ...` line in the header block. `tdmg.portability` blanks line 1
with any version, date and time. The rule above allows only the measured line, at the
measured position, from the pinned versions.

## Limits

- One machine, one day, two runs. The runs were 10 minutes apart, so the timestamps
  differ only in minutes. A run on another day changes the date in the same lines.
  Whether anything else changes on another day was not run.
- Another machine (the Mac, or another OS) was not tested. Byte-identical here does
  not show byte-identical across machines.
- The runs did not compare against the original runs of 2026-11-10 to 2026-11-16,
  except for the two `selection.json` files and the Roadie `model.3mf` above.

- **major — The gate does not define what qualifies as printable.** [docs/PLAN.md:75](../../../docs/PLAN.md#L75): “Run the checks for this print type”; line 11 promises a printable file. **Evidence:** No mandatory check set or PASS/FAIL/UNKNOWN policy is specified. A watertight solid can exceed the bed, contain unprintable walls, or trap supports inside a joint. The landscape report explicitly identifies these failures, yet S7 is optional. **Suggested fix:** Define required checks per recipe: dimensions/build volume, thickness/features, connectivity, support requirements, stability, joint clearance and material compatibility. Missing required measurements must produce UNKNOWN, preventing an unconditional printability verdict.

- **major — Validation occurs too late for some operations and too early for the delivered artifact.** [docs/PLAN.md:74](../../../docs/PLAN.md#L74): S3 adds bases, hinges and connectors before S4/S5; S6 exports afterward. **Evidence:** [Manifold requires manifold input](https://raw.githubusercontent.com/elalish/manifold/master/README.md), so a defective generated mesh can fail during base booleans before reaching repair. Export and placement can subsequently alter tessellation, topology or physical bounds. The report itself requires checking meshes after CAD export. **Suggested fix:** Normalize units and scale, validate/repair incoming geometry, add features, then validate again after tessellation and serialized-file read-back. Require an explicit unit assumption for STL checking; evaluate 3MF units and instance transforms. Apply target scaling before adding absolute-clearance features.

- **major — Cross-machine byte determinism is unsupported, and the cache contract is incomplete.** [docs/PLAN.md:20](../../../docs/PLAN.md#L20): “Nondeterminism is limited to two fenced stages”; line 214 requires identical SHA-256 “across runs and machines.” **Evidence:** The smoke record establishes only narrow local repeatability. [Trimesh’s source](https://raw.githubusercontent.com/mikedh/trimesh/5.2.0/trimesh/creation.py) automatically selects the first installed triangulation engine; the smoke script leaves that choice implicit. OCCT tessellation, native builds, floating-point behavior, sampling, slicer profiles and serialization remain additional variables. An image-only cache key also cannot distinguish changed models or parameters. **Suggested fix:** Promise byte reproducibility within a defined, pinned execution environment; use geometric tolerances across platforms. Explicitly select engines and tessellation settings. Key caches by complete stage configuration and upstream artifact hashes. Replay saved ML outputs; allow unavailable hosted weights hashes/seeds to be recorded as unavailable.

- **major — Hausdorff distance alone cannot protect functional geometry during repair.** [docs/PLAN.md:217](../../../docs/PLAN.md#L217): “Above a threshold, the run fails rather than silently changing the shape.” **Evidence:** A small geometric change can close a hinge opening or remove a thin connector while remaining below a distance threshold. The report calls for component, genus, volume and area changes as well. Moreover, [PyMeshLab’s Hausdorff filter](https://pymeshlab.readthedocs.io/en/latest/filter_list.html#get-hausdorff-distance) samples one direction and can exclude points beyond `maxdist`; its result is not automatically a certified maximum. **Suggested fix:** Specify a two-sided measurement method and its approximation limits, preserve intended bodies and functional features, recheck gaps and connections, and bound repair attempts. Unsupported measurements should fail or return UNKNOWN.

- **major — The example clearance rule combines incompatible measurements and calibration scopes.** [docs/PLAN.md:178](../../../docs/PLAN.md#L178): `clearance.print_in_place.per_side`, `applies_to: [G4, G5, C5]`, `range: [0.2, 0.5]`; line 204 says calibration “Overrides all others for that printer.” **Evidence:** The articulation note, line 28, distinguishes DrLex’s approximately 0.5 mm **vertical** clearance from `(3.6−2.5)/2 = 0.55 mm` radial clearance—already outside this range. [Prusa’s guidance](https://help.prusa3d.com/article/modeling-with-3d-printing-in-mind_164135) gives no universal value and distinguishes moving joints from friction fits. The notes also document different outcomes after changing the same printer’s slicing profile. **Suggested fix:** Separate XY/radial, diametral, Z and first-layer measurements, plus moving-joint versus assembly-fit rules. Bind calibration to joint family, material, nozzle and slicer/process-profile hash; invalidate it when those conditions change.

- **major — The taxonomy would reject valid jobs and cannot express common combinations.** [docs/PLAN.md:29](../../../docs/PLAN.md#L29): one geometry class plus one color/assembly strategy; C1 is “One body”; G3/G5 × C4 are forbidden; G4/G5 × C5 are forbidden. **Evidence:** A single-color articulated chain contains multiple bodies. A striped figurine can use layer changes: [Prusa’s implementation schedules changes by layer](https://help.prusa3d.com/article/color-change_1687), without a flat-geometry restriction. Small badges can use separately printed inlays; assembly is not limited to large signs. A model can also combine assembled parts with multicolor printing. G3 × C2 does not inherently require part-aware *generation*: later deterministic cuts can create color volumes. **Suggested fix:** Separate color encoding, assembly/layout and articulation attributes. Distinguish “not implemented” from physically incompatible combinations. Permit multiple bodies under C1 and generate CLI capability checks from this representation.

- **major — The permissive-core license claim is false for the native dependency chain.** [docs/PLAN.md:226](../../../docs/PLAN.md#L226): “Core dependencies (all permissive licenses)”; line 238 restricts core licenses to MIT/BSD/Apache. **Evidence:** The included OpenCASCADE kernel is [LGPL-2.1 with an additional exception](https://raw.githubusercontent.com/Open-Cascade-SAS/OCCT/master/README.md). The wrapper’s license does not replace the kernel’s. Optional installation also does not, by itself, resolve restrictions on imported/copied code, model weights or distributed datasets. **Suggested fix:** Explicitly decide whether LGPL-with-exception is acceptable, or move the CAD route outside the strict core. Register transitive native libraries, weights and fixture licenses separately, with version-specific obligations.

- **major — The proposed macOS slicer interface assumes unavailable JSON output.** [docs/PLAN.md:234](../../../docs/PLAN.md#L234): Orca has “JSON statistics,” alongside the M5 target and S7 parser. **Evidence:** In [OrcaSlicer v2.5.0 source](https://raw.githubusercontent.com/OrcaSlicer/OrcaSlicer/v2.5.0/src/OrcaSlicer.cpp), `record_exit_reson` writes `result.json` inside a Linux-only guard; the nearby comment explicitly excludes macOS and Windows. This contradicts an explicit caveat in the report. No slicer was run in the verification record. **Suggested fix:** Define and test a macOS-specific adapter using available logs/output artifacts. Pin the slicer and resolved profiles. Require actual nonempty sliced output and expected objects/materials, rather than accepting exit code zero alone.

- **major — Mesh complexity and memory budgets are absent despite the 16 GB constraint.** [docs/PLAN.md:73](../../../docs/PLAN.md#L73) and [docs/PLAN.md:76](../../../docs/PLAN.md#L76): heightfield generation and voxel remeshing have no resolution, triangle or memory limits; decimation is absent. **Evidence:** A read-only arithmetic check produced `2093058` triangles for the top surface of a 1024² heightfield. A dense 300 mm cube at 0.1 mm pitch requires `108.0 GB` for one float32 grid. [Orca’s source](https://raw.githubusercontent.com/OrcaSlicer/OrcaSlicer/v2.5.0/src/OrcaSlicer.cpp) enforces a configurable triangle-count limit. These problems arise before heavyweight ML. **Suggested fix:** Add input-resolution and triangle budgets, pre-allocation memory estimates, timeouts, and a tested sparse/chunked remeshing approach. Add decimation with protected boundaries and measured error, followed by validation.

- **major — Color generation is represented as packaging without a complete processing contract.** [docs/PLAN.md:77](../../../docs/PLAN.md#L77): S6 writes extruder assignments; line 262 delivers a “Paint-attribute encoder.” **Evidence:** Encoding paint does not obtain texture colors, quantize them to filaments, or transfer them onto repaired geometry. Remeshing changes triangle identities and can invalidate paint/UV associations. [Prusa documents](https://help.prusa3d.com/article/multi-material-painting_262620) that slicing can merge narrow painted regions into neighboring colors, so a correct-looking imported model is insufficient. Likewise, HueForge-style output needs a calibrated optical/stack model, not merely depth plus swap heights. **Suggested fix:** Define recipe-specific color stages: palette/regions before C2 extrusion; color transfer onto final geometry before C3 encoding; optical calibration and layer quantization for C4. Validate sliced material regions and layer changes.

- **minor — The “independent oracles” compare different predicates.** [docs/PLAN.md:211](../../../docs/PLAN.md#L211): trimesh watertightness, manifold3d status and `IsManifoldAndOriented` “must agree.” **Evidence:** [Trimesh defines watertightness](https://trimesh.org/trimesh.base.html#trimesh.base.Trimesh.is_watertight) by edge incidence and exposes winding consistency separately. Reversing one face preserves edge incidence while breaking orientation. Such disagreement is expected, not evidence that either library is wrong. None of this establishes self-intersection detection. **Suggested fix:** Define each predicate precisely and compare equivalent tests, with shared preprocessing and tolerances. Use analytic negative fixtures before treating Thingi10K labels as an oracle. Keep broad cross-library comparisons in tests rather than requiring duplicated computation everywhere.

- **minor — An existing Python paint writer is overlooked.** [docs/PLAN.md:47](../../../docs/PLAN.md#L47): “No open-source Python writer exists, so we would build one”; repeated at line 262. **Evidence:** The [Clonephaze add-on’s Python API documentation](https://raw.githubusercontent.com/Clonephaze/3MF-Blender-Add-on---Maintained/master/docs/guide.rst) explicitly documents Orca/Bambu `paint_color` and Prusa `slic3rpe:mmu_segmentation` export. The repository’s multicolor note already identifies this add-on. **Suggested fix:** Replace the absolute absence claim with a narrower statement about any unmet standalone/permissive requirement. Evaluate its API and fixtures before budgeting a new implementation; assess its copyleft components before reuse.

- **minor — Installation evidence is overstated.** [docs/PLAN.md:225](../../../docs/PLAN.md#L225): “Every candidate package installed from wheels and imported on the M5, except … CGAL.” **Evidence:** The report’s erratum explicitly says `bpy` resolved but **was not installed**. The verification README distinguishes resolver checks, imports and functional checks, and says no perception model or generative backend ran. **Suggested fix:** Preserve those separate verification states in the dependency register. Describe Python 3.13 as the supported choice from the recorded checks, without promoting resolution/import results into runtime validation.

- **minor — Several exit criteria cannot establish the claimed capability.** [docs/PLAN.md:257](../../../docs/PLAN.md#L257): “Opens … with the colors already assigned”; line 258: “matches the preview”; line 259: “Gate passes on N sample images.” **Evidence:** Import appearance does not establish printable color regions; `N` and the corpus are undefined; “matches” has no stated viewing conditions or tolerance. The G3 phase has no physical-print exit. Also, Q4 defaults to G1 → G1 multicolor → G3, while the roadmap inserts G2 first. **Suggested fix:** Specify named fixtures, counts, expected failures, dimensional/color criteria and representative physical prints. Define permitted break-in and repeatability for joints. Resolve the default phase order. Start with one complete print-and-check recipe before expanding the full framework.

- **minor — Evidence tiers conflate provenance with demonstrated validity.** [docs/PLAN.md:203](../../../docs/PLAN.md#L203): source code or an official document qualifies as “primary” and can supply a default; line 206 permits choosing a default inside a disagreement range. **Evidence:** Source code proves what a program does, not that its physical rule works. The articulation notes label an unprinted generator’s dimensions as primary-source assertions. Conflicting values may describe different axes, processes or fit types; averaging or selecting between them does not establish applicability. **Suggested fix:** Track provenance, applicability and validation status separately. Distinguish normative format constraints, empirical printer rules and engineering hypotheses. Experimental physical defaults should require an explicit experimental status; calibration must never override format constraints.

- **minor — The documentation machinery checks presence, not agreement, and front-loads maintenance.** [docs/PLAN.md:166](../../../docs/PLAN.md#L166): generation covers rule/check/dependency tables; lint checks IDs, citations and headings. **Evidence:** Those checks permit a valid check ID to be attached to the wrong recipe or omitted from runtime requirements. The compatibility matrix and CLI restrictions have no specified shared source. Phase 0 moves research directories, while example references still use their old paths. Five documentation layers and a page/module per taxonomy entry precede the first printed recipe. **Suggested fix:** Begin with a newcomer guide, one recipe page and a small shared recipe/rule registry. Generate required-check and compatibility tables from runtime declarations. Validate citation targets and fragments, maintain stable research links, and add layers as implemented recipes require them.

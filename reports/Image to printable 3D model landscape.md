# Deterministic code turns images into reliable prints

In November 2026 the most reliable way to turn a user's image into an FDM-ready STL or 3MF file is a deterministic Python pipeline. Machine learning handles only the three jobs no rule can do: cutting the subject out of a photo, estimating depth, and inventing 3D shape the camera never saw. Code, not model judgment, decides whether the result is printable. The building blocks for everything that ends up flat or 2.5D exist today as arm64 Python packages, most of them permissively licensed. That covers silhouette extrusions, keychains, cookie cutters, lithophanes, reliefs, HueForge-style filament paintings, AMS color plates and flat flexis. The research found these building blocks but did not benchmark complete workflows on the M5. Filament painting and flat flexis still lack an open, automatic, permissively licensed implementation. True 3D from a single photo is a different regime. Step1X-3D documents a watertight intermediate representation, but no generator has been shown independently to produce FDM-ready meshes that need no repair. The open-weights leader, TRELLIS.2, explicitly supports open and non-manifold surfaces. The only quantified figure is a vendor's own: 55% of Meshy's models were watertight straight out of export. Almost every upstream model repo is CUDA-only. On 16 GB, only shape-only community ports of Hunyuan3D 2.1 (about 7.85 GB peak), TRELLIS.2 and Pixal3D are plausible, so hosted inference at roughly $0.02–$0.60 per model is the realistic default. In both regimes, success depends on a print-readiness gate with four parts: the 3MF core spec's MUST rules (every edge shared by exactly two triangles, consistent outward orientation, positive volume), a repair ladder that tries detail-preserving fixes before volumetric rebuilds, FDM geometry checks, and a slicer command-line run as an outside check. OrcaSlicer 2.5 is the only mainstream slicer with documented, scriptable repair on macOS. Articulated and multi-color prints add their own rules. Joint clearances are absolute and must not scale with the model. The only dimensioned flat-flexi hinge spec uses about 0.5 mm of vertical and 0.55 mm of radial clearance. No validated FDM ball-joint numbers exist. Each extra filament on a layer costs a full purge on AMS-class machines. Extruder assignment lives in slicer-specific 3MF sidecar files. earthtojake/text-to-cad is a popular MIT-licensed text-to-CAD agent toolkit built on build123d, not an image-to-mesh tool. Its printability checks and "measure, never eyeball" rules are worth copying, but it should not be a dependency. Cited claims are primary-verified (repos, specs, source code, official docs, install tests on the target Mac) unless marked *secondary* (vendor blogs, press, forums, search-result snippets).

## Flat and relief prints need machine learning only for the mask

When the printable form of an image is flat or 2.5D, every stage after the foreground mask is deterministic and scriptable.

- **Tracing.** OpenCV's `findContours` with `RETR_CCOMP` returns a two-level hierarchy in which the second-level contours are holes ([OpenCV docs](https://raw.githubusercontent.com/opencv/opencv/4.x/doc/py_tutorials/py_imgproc/py_contours/py_contours_hierarchy/py_contours_hierarchy.markdown)). **vtracer** (MIT, 7,485 stars, macOS arm64 wheels for CPython 3.11–3.14) traces binary or color-clustered rasters. Its `cutout` mode emits non-overlapping color regions instead of stacked ones ([vtracer](https://github.com/visioncortex/vtracer), [PyPI](https://pypi.org/project/vtracer/)). potrace suppresses speckles and can output pure polygons, but it is GPL-2.0 ([potrace](https://potrace.sourceforge.net/potrace.1.html)).
- **Cleanup.** Shapely 2.x repairs the traced shapes. `make_valid(method='structure')`, added in 2.1, rebuilds rings; `buffer` dilates or erodes; `simplify(preserve_topology=True)` keeps geometry valid ([make_valid](https://shapely.readthedocs.io/en/stable/reference/shapely.make_valid.html), [Shapely manual](https://shapely.readthedocs.io/en/stable/manual.html)).
- **Extrusion.** `trimesh.creation.extrude_polygon` turns a polygon with holes into what its docs call a "watertight body" ([trimesh.creation](https://trimesh.org/trimesh.creation.html)).
- **CAD routes.** build123d adds a B-rep route: `import_svg` reads SVG, and `Mesher` writes multi-part 3MF. CadQuery cannot import SVG at all ([build123d](https://build123d.readthedocs.io/en/latest/import_export.html), [CadQuery](https://cadquery.readthedocs.io/en/latest/importexport.html)). OpenSCAD's `import()` reads SVG, but it applies `dpi` only when width and height lack absolute units; `dpi=25.4` makes one SVG unit equal one millimetre ([OpenSCAD manual](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/SVG_Import)).

The failures that matter in practice come from the 2D data, not the extrusion. One Bambu forum user tried to reproduce MakerLab's Image to Keychain offline. A FreeCAD SVG import produced more than **100,000 curves**, and a 3MF round trip gave either hundreds of separate unsliceable objects or one solid slab that could not be painted ([Bambu forum](https://forum.bambulab.com/t/offline-method-to-recreate-the-image-to-keychain-makers-results/89827)). Other users report non-manifold edges in the official keychain output itself ([Bambu forum](https://forum.bambulab.com/t/image-to-keychain-error/112729)). Shapely's docs also warn that `make_valid` can return a GeometryCollection and that `buffer(0)` can split a polygon into several pieces ([Shapely manual](https://shapely.readthedocs.io/en/stable/manual.html)). Robust code therefore does four things:

1. Iterate over every polygon part instead of assuming one.
2. Rescale to one authoritative target width in millimetres instead of trusting SVG or raster units.
3. Shrink then regrow each shape by about half a nozzle width, which deletes slivers no nozzle can print.
4. Drop islands smaller than roughly (2 × nozzle)².

The research team derived these rules from nozzle geometry; no source publishes them.

Perception is the only stage that needs a model. On the Mac, the options differ mainly in licence and acceleration:

- **rembg** (MIT, 25,389 stars) ships local ONNX models. Its default `bria-rmbg` weights are about 1 GB and "require a paid agreement for commercial use". Its docs cover CPU, CUDA and ROCm and never mention Apple Silicon ([rembg](https://github.com/danielgatis/rembg)). ONNX Runtime's official macOS wheel includes a Core ML execution provider ([ONNX Runtime](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html)), but user reports on whether it actually uses the GPU are mixed (*secondary*, [GitHub issue](https://github.com/hacksider/Deep-Live-Cam/issues/357)).
- **Apple Vision.** Apple's `VNGenerateForegroundInstanceMaskRequest` (macOS 14+) produces masks for any foreground object, without needing a class label. Python can call it through `pyobjc-framework-Vision` 13.0 ([Apple docs](https://developer.apple.com/tutorials/data/documentation/vision/vngenerateforegroundinstancemaskrequest.md), [PyPI](https://pypi.org/project/pyobjc-framework-Vision/)).
- **SAM 3.** Meta's official code still depends on Triton, which is CUDA-only. The pull request adding Apple-GPU (MPS) and CPU inference was still unmerged in late October 2026 ([HF discussion](https://huggingface.co/facebook/sam3/discussions/11), [PR #627](https://github.com/facebookresearch/sam3/pull/627)). An Apache-2.0 port to MLX, Apple's machine-learning framework (0.8B parameters, about 3.4 GB), runs text- and box-prompted segmentation on Apple Silicon ([mlx-community/sam3-image](https://huggingface.co/mlx-community/sam3-image)).
- **No model.** For photos shot against a plain backdrop, seehiong/printable shows a deterministic background keyer ([printable](https://github.com/seehiong/printable)).

Reliefs and lithophanes are equally tractable. A lithophane is a numpy thickness map on a base plate. The only primary-source rule found is LithophaneMaker's: minimum thickness at least **1.5× the nozzle diameter** ([LithophaneMaker](https://www.lithophanemaker.com/Lithophanes.html)). The common 0.8–3 mm thickness band comes from vendor guides (*secondary*, [JLC3DP](https://jlc3dp.com/blog/lithophane-3d-print)). OpenSCAD's `surface()` reads a PNG directly as a brightness heightmap ([OpenSCAD manual](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/Importing_Geometry)).

For bas-relief from estimated depth, **Depth Anything V2 Small** is the clean Mac choice: Apache-2.0, 24.8M parameters, with a Core ML conversion published by Apple. Its Base and Large variants are CC-BY-NC-4.0 ([Depth Anything V2](https://github.com/DepthAnything/Depth-Anything-V2), [Apple Core ML](https://huggingface.co/apple/coreml-depth-anything-v2-small)). Marigold runs on Apple's GPU via an `--apple_silicon` flag, but it is a slow diffusion model and its weights are RAIL-licensed ([Marigold](https://github.com/prs-eth/Marigold)). The classical step that makes estimated depth printable is gradient-domain depth compression ([Weyrich et al. 2007](https://gfx.cs.princeton.edu/pubs/Weyrich_2007_DBF/relief.pdf)). No paper or tool validates learned-depth reliefs as physical prints. The closest open tools, Bigchx/mcp_3d_relief and seehiong/printable, are partial starting points ([mcp_3d_relief](https://github.com/Bigchx/mcp_3d_relief), [printable](https://github.com/seehiong/printable)).

Filament painting builds color from stacked translucent layers, with a filament swap at set heights. HueForge dominates it commercially. It is closed source, maps brightness to layer height using each filament's measured Transmission Distance, runs on Apple Silicon, and exports STL plus a text list of swap heights, but not 3MF ([HueForge](https://shop.thehueforge.com/pages/about-hueforge)). The open alternatives are real but carry licence restrictions:

- **Lumina Layers:** AGPL-3.0-only, 1,190 stars, macOS Apple Silicon, calibrated-lookup-table approach, 3MF output ([Lumina Layers](https://github.com/lumina-layer-studio/Lumina-Layers)).
- **Kromacut:** AGPL-3.0, TypeScript ([Kromacut](https://github.com/vycdev/Kromacut)).
- **AutoForge:** CC BY-NC-SA 4.0, a PyTorch optimizer that supports Apple's GPU ([AutoForge](https://github.com/hvoss-techfak/AutoForge)).

For any shipped tool, the AGPL network clause and the non-commercial clause both matter. On the slicer side, a layer-based color change in PrusaSlicer just inserts an M600 pause command ([Prusa KB](https://help.prusa3d.com/article/color-change_1687)).

Template objects reduce to polygon offsets. Open cookie-cutter generators default to **0.8 mm walls, 10 mm cutter height with a 3 mm wedge, and 4 × 1 mm flanges** ([cookieCutterStlGenerator](https://github.com/CZDanol/cookieCutterStlGenerator)). The OpenSCAD route is slow: one generator needs a nightly build to cut an example from about 30 minutes to 50 seconds ([cookie-cutter-generator](https://github.com/Papooch/cookie-cutter-generator)). Shapely's offset engine avoids that cost. Bambu's MakerLab, launched in March 2024 with sign, vase and pixel-puzzle makers, proves the product category ([Bambu blog](https://blog.bambulab.com/new-launch-of-makerlab-experiments)), and the stack above can reproduce its deterministic tools. What does not exist is a maintained, permissively licensed Python package for the whole chain from image to validated, nozzle-aware, multi-body 3MF. The nearest are ChromaPrint3D (Apache-2.0, 91 stars, C++ core, images to multi-color 3MF with Bambu presets) and colorplate (MIT, one watertight STL per color) ([ChromaPrint3D](https://github.com/Neroued/ChromaPrint3D), [colorplate](https://pypi.org/project/colorplate/)). Many 2026 entrants are thin wrappers for AI agents (agent skills or MCP servers) rather than libraries.

## Photo-to-3D generation is the one stage that needs the cloud

The open-weights frontier moved fast in 2025–2026, but none of it was built for a 16 GB Mac or for printing.

- **TRELLIS.2** (Microsoft; 4B parameters, MIT, December 2025) requires "an NVIDIA GPU with at least 24GB of memory". Its O-Voxel representation "robustly handles... Open Surfaces... Non-manifold Geometry" ([TRELLIS.2 README](https://raw.githubusercontent.com/microsoft/TRELLIS.2/main/README.md)). That suits game assets and works against slicers.
- **Hunyuan3D 2.0 and 2.1** (Tencent) need **6 GB and 10 GB** for shape generation. Their community licence "does not apply in the European Union, United Kingdom and South Korea" ([Hunyuan3D-2 LICENSE](https://raw.githubusercontent.com/Tencent-Hunyuan/Hunyuan3D-2/main/LICENSE), [Hunyuan3D-2.1 README](https://raw.githubusercontent.com/Tencent-Hunyuan/Hunyuan3D-2.1/main/README.md)). Versions 2.5, 3.0 and 3.1 are API-only, and private deployment is "Not supported" ([Tencent Cloud FAQ](https://intl.cloud.tencent.com/document/product/1284/75301)).
- **Pixal3D** (Tencent ARC; MIT, SIGGRAPH 2026) builds on the TRELLIS.2 backbone ([licence](https://huggingface.co/TencentARC/Pixal3D/raw/main/LICENSE)).
- **Hi3D v1.0** (released 23 October 2026) only refines geometry. It is Linux/CUDA-only with "no CPU inference path", and it normalizes output "to unit maximum radius, so... absolute scale [is] not preserved" ([Hi3D README](https://raw.githubusercontent.com/hi3d-official/Hi3Dv1.0/main/README.md)).

Hosted inference is cheap, so choosing between local and cloud is about privacy and latency, not money. The research did not compare how providers retain, use for training, or delete uploaded photos, so that comparison is still open.

- **fal.ai** charges **$0.02** per TRELLIS generation and **$0.25–$0.35** per TRELLIS.2 generation, depending on resolution ([fal TRELLIS](https://fal.ai/models/fal-ai/trellis), [fal TRELLIS.2](https://fal.ai/models/fal-ai/trellis-2)).
- **Replicate** runs Hunyuan3D-2 for about $0.04 per run on an L40S GPU ([Replicate](https://replicate.com/tencent/hunyuan3d-2)).
- **Hugging Face ZeroGPU** gives free accounts five GPU-minutes a day and PRO accounts 40 minutes, plus $1 per extra ten minutes ([ZeroGPU docs](https://huggingface.co/docs/hub/spaces-zerogpu)). On 8 November 2026, Spaces for Hunyuan3D 2/2.1, TRELLIS.2, Pixal3D, Hi3D v1 and TripoSG were running ([HF API](https://huggingface.co/api/spaces/microsoft/TRELLIS.2)).
- **Commercial APIs** land at **$0.20–$0.60 per model**, by the research team's arithmetic from published credit tables. Meshy Pro is $20 for 1,000 credits, with mesh-only image-to-3D at 20 credits. Tencent bills $0.02 per credit, with untextured "Geometry" generation at 15 credits. Tripo prices credits at $0.01, with untextured image-to-3D at 20 credits ([Meshy pricing](https://www.meshy.ai/pricing), [Meshy API pricing](https://docs.meshy.ai/api/pricing), [Tencent billing](https://www.tencentcloud.com/document/product/1284/75281), [Tripo v3.1](https://developers.tripo3d.com/en/models/v3-1)).

Single-color prints need geometry only, so the cheaper untextured modes are the right ones. Output ownership varies: Meshy's free tier licenses outputs as CC BY 4.0 ([Meshy pricing](https://www.meshy.ai/pricing)). Output terms do not settle rights in the input image itself, such as artwork or characters it depicts. The research did not cover those rights.

What none of these models delivers is a printable solid:

- **Floaters and degenerate faces.** Hunyuan3D-2 ships a `FloaterRemover` and a `DegenerateFaceRemover` because these defects are expected ([postprocessors.py](https://raw.githubusercontent.com/Tencent-Hunyuan/Hunyuan3D-2/main/hy3dgen/shapegen/postprocessors.py)).
- **Inner shells.** A TRELLIS.2 issue reports that "most generations add an entire inner shell". The only workarounds are ray-cast scripts that take minutes per mesh ([issue #140](https://github.com/microsoft/TRELLIS.2/issues/140)).
- **Double surfaces.** Pixal3D's optional remesh makes two parallel surfaces joined through tiny holes, "unsuitable for 3D printing" ([issue #18](https://github.com/TencentARC/Pixal3D/issues/18)).
- **Mac port output.** The author of the Pixal3D Apple-GPU port writes that its meshes "are not certified watertight or print-ready" ([PR #35](https://github.com/TencentARC/Pixal3D/pull/35)).

Most telling for Mac users: a non-CUDA port of TRELLIS.2 produced **about 220,000 open boundary edges where the CUDA reference output was watertight**. The reporter traced this to hard `> 0` thresholds that flip under small cross-platform half-precision (fp16) differences ([issue #169](https://github.com/microsoft/TRELLIS.2/issues/169)). The same model and seed can therefore yield different topology on different hardware, so every Mac port needs its own validation.

The only quantified comparison is vendor-run. Meshy's own 75-model benchmark found 55% of its models watertight straight out of export and 97% of its figurines slicing in Bambu Studio (*secondary*, [Meshy blog](https://www.meshy.ai/blog/best-ai-tools-for-3d-printing)). A census of 23 generators that looked independent was run by a repair-tool vendor. It withheld its watertight and non-manifold columns and retracted its earlier per-generator figures ([3dqa-benchmark README](https://raw.githubusercontent.com/alza123123/3dqa-benchmark/main/README.md), [Topoheal census](https://topoheal.com/census/)). Cyc3D, a 2026 image-to-3D benchmark, measures structure and texture-map quality but names no watertight or manifold metric ([Cyc3D](https://arxiv.org/abs/2608.28080)).

Meshy is the only vendor with a documented, machine-readable printability API. Its free `print/analyze` endpoint returns `is_watertight`, hole count, non-manifold edges, degenerate faces, and an FDM thin-wall check (1.0 mm floor) at a stated print size. It also accepts STL or GLB URLs from outside Meshy, so it can cross-check any generator. Its paid repair returns a watertight mesh but strips textures ([Analyze Printability](https://docs.meshy.ai/api/analyze-printability.md), [API pricing](https://docs.meshy.ai/api/pricing)). Tripo's `generate_parts` (+20 credits, geometry only) and Tencent's 3D part generation (30 credits) split models into parts ([Tripo v3.1](https://developers.tripo3d.com/en/models/v3-1), [Tencent billing](https://www.tencentcloud.com/document/product/1284/75281)). Hi3D advertises split-to-print with connectors and a tolerance system (*secondary*, [3Dnatives](https://www.3dnatives.com/en/ai-3d-model-generators-3d-printing-13082026/)).

Printer makers' generators converge on constrained figurines. Bambu's PrintU turns a portrait into a Hunyuan-based figure whose back is "reconstructed speculatively" (*secondary*, [igor'sLAB](https://www.igorslab.de/en/bambu-lab-printu-from-portrait-photo-to-3d-figure-comfortable-fast-but-not-without-hooks/)). Publishing has its own gate. Bambu said in November 2026 that MakerWorld will not split content into AI and non-AI categories. It is instead building model-quality checks and AI-image detection, because "an AI-generated image can promise a level of quality that the model simply cannot deliver once printed" ([Bambu blog](https://blog.bambulab.com/first-time-together-makerworld-makers-from-across-the-u-s-meet-in-san-jose/)).

Two existing open-source end-to-end projects show the trade-off. **3Dify** wraps Hunyuan3D 2.1 with trimesh repair but needs an NVIDIA GPU with at least 16 GB ([3Dify](https://github.com/ThatButters/3Dify)). **idea-to-print** is the closest existing blueprint for this project, though it is tied to a cloud generator and Blender:

- It drives Hunyuan3D 3.1 through Tencent's cloud API.
- It merges a base and auto-thickens thin strokes.
- It runs self-intersection, per-face thickness, contact-area and center-of-mass checks, each reporting PASS, FAIL or UNKNOWN.
- It slices offline through a local Bambu Studio command-line run on macOS ([idea-to-print](https://github.com/Rjxshr1/idea-to-print/blob/main/README.en.md)).

Single-color printing is the case where local generation is most viable. FDM needs only geometry, and the shape-only path fits in memory most easily. Multi-color from a photo is harder locally. Texturing is the memory hog, and only one textured local example on 16 GB was found. There are two routes from a texture to AMS colors. Meshy's Multi-Color Print is commercial (10 credits) ([Meshy API pricing](https://docs.meshy.ai/api/pricing)). OrcaSlicer 2.5 (AGPL-3.0) can import a textured model in its GUI. It clusters the texture colors, matches them to filaments, and applies the result as paint ([Plater.cpp](https://raw.githubusercontent.com/OrcaSlicer/OrcaSlicer/v2.5.0/src/slic3r/GUI/Plater.cpp)). A headless path for that import was not verified. Neither route produces separate watertight shells, one per color.

Environment planning matters as much as memory. In install tests on the target Mac, the full mesh stack installed from prebuilt wheels on CPython 3.12: trimesh, manifold3d, pymeshfix, PyMeshLab, MeshLib, lib3mf, libigl, Open3D, the CGAL bindings, build123d and cadquery-ocp. A second test on CPython 3.13 installed and imported the same stack, except the CGAL bindings, whose wheels stop at cp312 ([verification record](../research/verification/2026-11-08-stack-smoke/README.md)). pymeshfix and libigl ship `cp312-abi3` wheels, which work on 3.13; pymeshfix 0.18.1 declares support below 3.15. Blender's `bpy` wheel exists only for Python 3.13 (version 5.2.3) or 3.11 ([bpy](https://pypi.org/project/bpy/)). orca123d needs 3.13 or later. So 3.13 is the recommended interpreter. PyPI's `pyopenvdb` has no macOS build at all, though conda-forge's `openvdb` does ([pyopenvdb](https://pypi.org/project/pyopenvdb/), [conda-forge openvdb](https://api.anaconda.org/package/conda-forge/openvdb)).

## A print-readiness gate assembles from permissive arm64 wheels

"Printable" has a formal core. For model objects, the 3MF core specification requires that "every triangle edge in the mesh shares common vertex endpoints with the edge of exactly 1 other triangle", that adjacent triangles share the same orientation, and that normals "point away from the interior". It applies a positive fill rule, under which a negative-volume mesh becomes a void. It also says producers "SHOULD NOT" emit self-intersections while consumers "MUST accept" them ([3MF Core spec](https://github.com/3MFConsortium/spec_core/blob/master/3MF%20Core%20Specification.md)). That last clause is why self-intersection can sit in the warning tier rather than cause a hard reject. The specification does not require a volumetric rebuild, so whether to rebuild is a choice for the pipeline.

The spec's definition has two direct checkers in Python:

- **lib3mf** provides `IsManifoldAndOriented()` (BSD-2-Clause, universal2 wheel) ([lib3mf docs](https://lib3mf.readthedocs.io/en/latest/source/Cpp/lib3mf_MeshObject.html), [PyPI](https://pypi.org/project/lib3mf/)).
- **manifold3d** uses the 3MF wording as its manifold definition and returns an explicit `NotManifold` error instead of guessing ([Manifold wiki](https://github.com/elalish/manifold/wiki/Manifold-Library), [Manifold](https://github.com/elalish/manifold)).

The research team's proposed check order maps one-to-one onto these libraries. The hard checks, in order: finite coordinates; no degenerate or duplicate faces; every edge shared by at most two faces; no pinched vertices; a closed surface; consistent winding; positive volume. Checks of a different kind follow. Self-intersection and an unexpected number of components are warnings. Build-volume fit and calibrated minimum wall and feature sizes are acceptance requirements, not warnings. OrcaSlicer itself rejects a plate whose objects do not fit the print volume ([OrcaSlicer.cpp](https://raw.githubusercontent.com/OrcaSlicer/OrcaSlicer/v2.5.0/src/OrcaSlicer.cpp)).

Licensing splits the toolbox. A permissive core detects every defect class and covers most repairs: trimesh (MIT), manifold3d (Apache-2.0), lib3mf (BSD-2), Open3D (MIT) and point-cloud-utils (MIT) ([trimesh](https://github.com/mikedh/trimesh), [Open3D header](https://raw.githubusercontent.com/isl-org/Open3D/main/cpp/open3d/geometry/TriangleMesh.h), [point-cloud-utils](https://github.com/fwilliams/point-cloud-utils)). The strongest general repair engines are copyleft or source-available ([PyMeshLab](https://pypi.org/project/pymeshlab/), [MeshFix](https://github.com/MarcoAttene/MeshFix-V2.1), [MeshLib licence](https://meshlib.io/license/)):

- **PyMeshLab** is GPL-3.
- **pymeshfix** wraps MeshFix, which "cannot be used for commercial purposes without a proper licensing contract".
- **MeshLib** is free only for non-commercial and educational use.

Each library also hides a trap:

- **MeshFix deletes parts.** It assumes "a single closed solid", and "by default, only the largest component is kept" ([MeshFix](https://github.com/MarcoAttene/MeshFix-V2.1)). In a local test, **pymeshfix's default `repair()` silently deleted one of two separate cubes.**
- **trimesh hole filling is weak.** Its `fill_holes` uses triangle fans that "may result in bad answers if the holes are non convex" ([trimesh.repair](https://trimesh.org/trimesh.repair.html)). In local testing it failed to close an eight-triangle hole.
- **Open3D scales badly.** Its self-intersection test checks every pair of triangles ([TriangleMesh.h](https://raw.githubusercontent.com/isl-org/Open3D/main/cpp/open3d/geometry/TriangleMesh.h)), so its cost grows with the square of mesh size.
- **Sign conventions disagree.** trimesh's signed distance is positive inside a mesh ([trimesh.proximity](https://trimesh.org/trimesh.proximity.html)); Open3D's is negative inside. A gate must normalize before combining libraries.

Repair should run from least to most destructive. Local fixes preserve geometry but cannot guarantee a solid: merge vertices, drop degenerate and duplicate faces, re-orient, fill small holes with PyMeshLab's bounded `meshing_close_holes(maxholesize=30)`, and split pinched vertices ([PyMeshLab filters](https://pymeshlab.readthedocs.io/en/latest/filter_list.html)). Volumetric rebuilds always produce a solid, but they resample the surface:

- **OpenVDB** converts a mesh to a level set and needs only "a closed surface but not necessarily a manifold surface". It ignores orientation and self-intersections ([OpenVDB](https://www.openvdb.org/documentation/doxygen/MeshToVolume_8h.html)).
- **manifold3d's `level_set`** turns any signed distance function into guaranteed-manifold output ([Manifold](https://github.com/elalish/manifold)).
- **point-cloud-utils' `make_mesh_watertight`** works, but in a local test it re-tessellated a 10-face cube into **10,960 faces** ([point-cloud-utils](https://github.com/fwilliams/point-cloud-utils)).

Code can measure detail loss deterministically: two-sided Hausdorff distance, plus changes in volume, area, genus and component count. PyMeshLab's `get_hausdorff_distance` measures one direction per call, so it must run both ways ([PyMeshLab filters](https://pymeshlab.readthedocs.io/en/latest/filter_list.html)). No vendor publishes acceptance thresholds. Setting voxel size to about half the nozzle width, so that only detail too small to print is lost, is the research team's engineering inference.

Two reference points frame the problem. Blender's 3D-Print Toolbox encodes the community checklist with concrete defaults: 1 mm minimum thickness, 45° overhang, and a 1e-4 threshold for zero area ([extension](https://extensions.blender.org/add-ons/print3d-toolbox/), [legacy add-on source](https://raw.githubusercontent.com/blender/blender-addons/main/object_print3d_utils/__init__.py)). Thingi10K shows the scale of the problem: of 10,000 real printing uploads, **50% are not solid, 45% self-intersect and 22% are non-manifold** ([Thingi10K](https://github.com/Thingi10K/Thingi10K)).

Geometry checks need fixed definitions because the methods disagree on the same shape. trimesh offers ray and inscribed-sphere thickness, MeshLib offers ray and in-sphere thickness at vertices, and PyMeshLab offers a shape-diameter function ([trimesh.proximity](https://trimesh.org/trimesh.proximity.html), [MeshLib thickness](https://meshlib.io/documentation/MRMeshThickness_8h.html), [PyMeshLab filters](https://pymeshlab.readthedocs.io/en/latest/filter_list.html)). On a unit cube in local tests, the ray method returned 1.0 at face centres, the sphere method 0.667, and rays fired from corners returned the 1.732 body diagonal. A gate should therefore fix one method per threshold, sample face centroids, and report where the thin regions are and how much of the surface was sampled. A low percentile is a useful summary but not a safe pass/fail rule. A narrow connector can be less than 5% of the samples and still decide whether the part survives, and face-count percentiles shift with tessellation. Critical features such as connectors and joints need their own checks. The remaining checks:

- **Overhang and support.** Overhang analysis is simple arithmetic on each face's normal, but no pure-Python library estimates FDM support volume. text-to-cad ships a "prism upper-bound" estimate ([manufacturing-printing.md](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/references/manufacturing-printing.md)). PySLM (LGPL-2.1) computes exact projected supports, but for metal processes ([PySLM](https://github.com/drlukeparry/pyslm)).
- **Orientation.** **Tweaker-3** (GPL-3.0, numpy only) is the only scriptable open-source FDM auto-orienter ([Tweaker-3](https://github.com/ChristophSchranz/Tweaker-3)). OrcaSlicer's `Orient.hpp` carries five trained constants identical to Tweaker-3's to 16 significant digits, without attribution, plus a penalty for bottom areas below 0.1 ([Orient.hpp](https://raw.githubusercontent.com/SoftFever/OrcaSlicer/main/src/libslic3r/Orient.hpp), [MeshTweaker.py](https://raw.githubusercontent.com/ChristophSchranz/Tweaker-3/master/MeshTweaker.py)). PrusaSlicer still has no FDM auto-orient; the request has been open since July 2024 ([PrusaSlicer issues](https://github.com/prusa3d/PrusaSlicer/issues?q=is%3Aissue+auto+orient)).
- **Stability.** Research systems such as Make It Stand never shipped as maintained libraries (*secondary*, [HAL](https://hal-univ-tlse3.archives-ouvertes.fr/INRIA/hal-00926855v1)). A centre-of-mass-over-footprint check is a few lines of trimesh, and idea-to-print already implements one ([idea-to-print](https://github.com/Rjxshr1/idea-to-print/blob/main/README.en.md)).

Numeric thresholds come from vendors, and they disagree in a predictable way. Service bureaus, which must succeed on any machine, publish larger minimums than printer makers. Encode each rule as a conservative/tuned pair, with the source attached:

| Rule | Conservative (shareable files) | Tuned personal printer |

The slicer is the final check, but each slicer misleads in its own way.

- **PrusaSlicer 2.9.7** repairs meshes at load but compiles out hole filling, because "the current algorithm does more harm than good on complex holes". Instead, it closes cracks narrower than twice a 0.049 mm radius in each slice ([TriangleMesh.cpp](https://raw.githubusercontent.com/prusa3d/PrusaSlicer/version_2.9.7/src/libslic3r/TriangleMesh.cpp), [slicing mode](https://help.prusa3d.com/article/slicing-mode_301501)). Its `--info` prints `manifold = yes|no` and `open_edges = N` as plain text ([Model.cpp](https://raw.githubusercontent.com/prusa3d/PrusaSlicer/version_2.9.7/src/libslic3r/Model.cpp)), and it exits with code 0 on "Nothing to print" ([CLI source](https://github.com/prusa3d/PrusaSlicer/tree/version_2.9.7/src/CLI)).
- **Windows-only repair.** PrusaSlicer's Netfabb repair is Windows-only ([FixModelByWin10.cpp](https://raw.githubusercontent.com/prusa3d/PrusaSlicer/version_2.9.7/src/slic3r/Utils/FixModelByWin10.cpp)), and so is Bambu Studio's ([Bambu wiki](https://wiki.bambulab.com/en/software/bambu-studio/fix-model)).
- **OrcaSlicer 2.5.0** (7 November 2026, universal macOS build) is the exception. Its rebuilt Fix Model works on Windows, macOS and Linux. `--repair` closes holes and cracks and removes local self-intersections. Parts that cannot become solid, "such as a single flat sheet", are left as they are and listed as failed ([Orca Fix Model wiki](https://github.com/OrcaSlicer/OrcaSlicer/wiki/prepare_stl_transformation#fix-model), [cli_transform](https://github.com/OrcaSlicer/OrcaSlicer/wiki/cli_transform), [Homebrew](https://formulae.brew.sh/api/cask/orcaslicer.json)). Its internal exit codes separate "no suitable objects" (−50), a validation error (−51) and the **1,000,000-triangle-per-plate limit** (−59); the `--mtcpp` option changes that limit. A calling process on macOS or Linux sees only the low eight bits of the status, so these arrive as **206, 205 and 197**, as checked on the target Mac. Its `result.json` warning report is compiled only on Linux. Its G-code statistics export, also JSON, is not behind that guard ([OrcaSlicer.cpp](https://raw.githubusercontent.com/OrcaSlicer/OrcaSlicer/v2.5.0/src/OrcaSlicer.cpp), [cli_actions](https://github.com/OrcaSlicer/OrcaSlicer/wiki/cli_actions)).
- **Cura** merges overlapping volumes by default ([fdmprinter.def.json](https://raw.githubusercontent.com/Ultimaker/Cura/main/resources/definitions/fdmprinter.def.json)).

One Python wrapper was found. estampo, formerly fabprint, describes itself as a build system for reproducible prints that wraps OrcaSlicer and CuraEngine, and it is in early development ([estampo](https://pypi.org/project/estampo/)). No in-process Python bindings exist for any slicer. No slicer was run during this research, so headless behavior on macOS is unverified. The consequence: close holes yourself, call slicers as subprocesses with explicit profiles, and treat their verdicts as a second opinion.

Output format and testing close the loop. 3MF is now an ISO standard (ISO/IEC 25422:2025) and carries units, objects, transforms and metadata ([3mf.io](https://3mf.io/)). Manifold's maintainers call STL "lossy and inefficient" ([Manifold](https://github.com/elalish/manifold)). trimesh writes 3MF but hard-codes `unit="millimeter"` and writes no metadata or color, and an issue requesting color support has been open since March 2026 ([threemf.py](https://raw.githubusercontent.com/mikedh/trimesh/main/trimesh/exchange/threemf.py), [#2517](https://github.com/mikedh/trimesh/issues/2517)). lib3mf sets units explicitly and validates on write. Bambu/Orca project files are a portability hazard. One placed a `type="other"` object in `<build>`, which the spec forbids, and PrusaSlicer closed the report without a fix ([PrusaSlicer#14286](https://github.com/prusa3d/PrusaSlicer/issues/14286)). For regression tests, the `thingi10k` package (Apache-2.0 code, per-model licences) filters the 10,000-model corpus by `closed`, `self_intersecting` and `solid` flags ([thingi10k](https://pypi.org/project/thingi10k/)). None of the surveyed geometry libraries promises deterministic output. Both 3MF writers add random identifiers. trimesh calls `uuid4()` for each object and for the build ([threemf.py](https://raw.githubusercontent.com/mikedh/trimesh/main/trimesh/exchange/threemf.py)), and lib3mf writes random UUIDs unless they are set ([verification record](../research/verification/2026-11-08-stack-smoke/README.md)). A gate should seed its samplers and set stable object and instance identities and archive metadata. It should assert byte-identical exports within one pinned environment and compare geometry within tolerances across platforms.

## Six print types fail in six different ways

Each target print type has a different binding constraint and a different dominant failure, so a single "printable" flag is not enough.

| Print type | Binding constraint | Dominant failure | Deterministic building blocks | Evidence quality |
|---|---|---|---|---|
| Complex 3D shape | Closed solid at a stated scale, printable walls, stable base | Generator holes, inner shells, floaters; fragile thin parts; tipping | Gate above; base merge; Tweaker-3; decimation | Checks strong; generator defect rates vendor-only |
| Single-color (any geometry) | Geometry only; color discarded | Same as its geometry class | Shape-only generation; STL or plain 3MF | Strong |
| Flat flexi | Pin-in-loop clearance near 0.5 mm vertical and 0.55 mm radial (one dimensioned source); link walls ≥2 extrusion widths | Joints fused at the first layer or Z seam; snapped links; fusion after downscaling | Shapely extrusion plus Flexifier/BOSL2 techniques | One dimensioned primary spec plus two FDM studies |
| Fully 3D articulated | Captive joints without supports; absolute clearance; minimum joint size | Fusion; supports trapped in joints; weak necks | Rigging models plus manifold3d booleans (no integrated tool) | No validated FDM ball-joint data |
| Multi-color AMS/MMU | Filaments per layer; region size; extruder metadata | Purge waste and time; colors lost on import; slivers | Multi-object 3MF plus slicer sidecars; per-triangle paint; lib3mf/build123d | Strong (slicer source); no texture-to-region tool |
| Single-color multi-plate | Build volume; cut placement; connector fit | Misfit connectors; visible seams; supports on cut parts | manifold3d plane splits plus dowel booleans; explicit plate assignment | Tolerances secondary only |

### Complex and single-color 3D shapes need scale, base and density set by code

Generators output geometry with no units. Hi3D normalizes everything to unit radius ([Hi3D](https://raw.githubusercontent.com/hi3d-official/Hi3Dv1.0/main/README.md)). Meshy's analyzer simply reads an STL's longest side as millimetres and assumes a 150 mm print height for GLB files ([Analyze Printability](https://docs.meshy.ai/api/analyze-printability.md)). The pipeline must set a target height before any thickness check means anything. Then it must add the features that make figurines printable. Meshy's own guide asks for a **base of at least 3 mm and 1.2 mm FDM walls**, and it warns that fine detail disappears at FDM resolution ([Meshy docs](https://docs.meshy.ai/en/webapp/guides/use-cases/3d-printing)). Printer makers' generators emphasize figurines and offer optional bases: Bambu's PrintMon (press coverage, *secondary*) and Creality's CubeMe ([Notebookcheck](https://www.notebookcheck.net/Bambu-Lab-s-PrintMon-Maker-creates-cute-3D-printable-characters-from-text-and-image-prompts.906452.0.html), [Creality wiki](https://wiki.creality.com/en/printers-general-documents/2d-image-into-3d-model)).

Triangle count is the next silent failure. Hunyuan3D reduces output to 40,000 faces by default ([postprocessors.py](https://raw.githubusercontent.com/Tencent-Hunyuan/Hunyuan3D-2/main/hy3dgen/shapegen/postprocessors.py)). A vendor census put median TRELLIS.2 output near 290,000 faces and TripoSG near 1.37 million (*secondary*, [Topoheal census](https://topoheal.com/census/)). OrcaSlicer refuses plates above 1,000,000 triangles by default ([cli_actions](https://github.com/OrcaSlicer/OrcaSlicer/wiki/cli_actions)), so mesh decimation belongs in the gate.

Orientation must account for layer strength. Prusa compares FDM prints to wood, stronger along the grain than across it ([Prusa KB](https://help.prusa3d.com/article/modeling-with-3d-printing-in-mind_164135)). Hobby and thesis tests put strength across layers at roughly 45–80% of strength along them (*secondary*, [CSUS thesis](https://scholars.csus.edu/esploro/outputs/graduate/Mechanical-and-FEA-comparison-of-FDM/99258311232901671)), so thin necks aligned with Z deserve a stricter threshold.

Single-color printing simplifies everything. Textures can be thrown away, so Meshy's texture-stripping repair costs nothing in quality. The shape-only generation modes are cheaper, and they are the only ones that fit on a 16 GB Mac.

### Flat flexis want about 0.5 mm of clearance and still need manual hinges

The only designer-published, dimensioned flat-flexi hinge is DrLex's "stronger links" Flexi Rex ([DrLex README](https://github.com/DrLex0/print3D-FlexiRex), [hinge drawing](https://github.com/DrLex0/print3D-FlexiRex/blob/master/images/Hinge_dimensions.png)):

- A **2.5 mm axle in a 3.6 mm hole**: 1.1 mm of diametral clearance, or **0.55 mm radial**.
- About **0.5 mm of vertical clearance** between the top of the axle and the shackle.
- Shackle walls of at least 1.58 mm.
- Gaps of 1.2–1.8 mm between body segments.
- Printed at 0.2 mm layers with three perimeters, 15% infill and no supports.

DrLex adds that extra clearance buys no flexibility: "the model will only become weaker". His radial clearance is roughly double the 0.2–0.3 mm per side quoted in 2026 vendor blogs (*secondary*, [Sovol](https://www.sovol3d.com/blogs/news/print-in-place-3d-printing-how-to-design-hinges-joints-and-moving-parts-that-actually-work), [JLC3DP](https://jlc3dp.com/blog/3d-printed-articulated-animals-design)).

The peer-reviewed FDM evidence falls in between:

- **2025 study:** 10 mm PLA pins printed assembled moved most easily at **0.15–0.25 mm** clearance ([Technologies 2025](https://doi.org/10.3390/technologies13100436)).
- **2023 print-farm study:** hinge axes aligned with Z tolerated tighter clearance than axes lying flat, and 0.1 mm layers "might lead to increased release forces" while 0.3 mm layers raised the force needed during motion (abstract only) ([Frohn-Sörensen 2023](https://italg.wiwi.uni-siegen.de/en/?p=2994)).
- **2023 University of Maryland comparison:** 0.2–0.3 mm gaps spun freely on good profiles, but a Bambu P1P "Strength" profile fused every gap up to 0.25 mm because of oversized Z seams ([UMD report](https://terrapinworks.umd.edu/sites/terrapinworks.umd.edu/files/P1P%20vs%20MK3%20Report%202023.pdf)).

Generator code is all over the map. Flexifier hard-codes 0.8 mm horizontal and vertical tolerance ([streamlit_app.py](https://github.com/Lucandia/Flexifier/blob/main/streamlit_app.py)). BOSL2 uses separate mechanisms ([hinges.scad](https://raw.githubusercontent.com/BelfrySCAD/BOSL2/master/hinges.scad)). Its print-in-place `knuckle_hinge()` defaults to `gap=0.2` between segments, and its pin holes are enlarged by 2 × `$slop`. `living_hinge_mask()` uses a hinge gap that defaults to the layer height, plus 2 × `$slop`. Minimum scale depends on the nozzle. Cenwulf's parametric Rex bottoms out near 54% scale on a 0.4 mm nozzle, because shackle walls must stay at least two extrusion widths thick ([FlexiRex-Fusion](https://github.com/Cenwulf/FlexiRex-Fusion)). Code should compute minimum scale from extrusion width rather than hard-code it.

The biggest gap is automation. This survey, run in November 2026 with a limited search budget, found no open-source tool that automatically splits a 2D silhouette into hinged links. The tools that do place joints automatically work on 3D STLs and are hosted services (*secondary*, [printpal](https://printpal.io/tools/flexi-model-creator)). Bächer et al. (2012) placed joints on the shape's medial axis (its centre line) while maximizing the smallest cross-section ([Bächer 2012](https://doi.org/10.1145/2185520.2185543)). That suggests a deterministic recipe that this survey did not find shipped anywhere: skeletonize the mask, then cut across the skeleton wherever the local width exceeds hinge diameter plus clearances and walls. Licensing favors reusing rules, not meshes. The Flexi Rex lineage is CC BY-SA ([DrLex README](https://github.com/DrLex0/print3D-FlexiRex)), and Flexifier's licence is ambiguous: AGPL-3.0 on GitHub, GPL-3.0 in its README ([Flexifier](https://github.com/Lucandia/Flexifier)).

### Fully 3D articulation has rigging models but no validated FDM joints

The only dimensioned ball-joint evidence predates consumer FDM. Calì et al.'s 2012 SIGGRAPH Asia system printed on SLS and PolyJet, not FDM. It found "a gap of 0.2mm is too small" because the parts fused, 0.3 mm gave easy movement with friction, and working joints needed **at least a 5 mm radius**. The authors calibrated each printer "before model generation", because "individual printers may vary" ([Calì 2012](https://reality.tf.fau.de/projects/jointfit/jointfit-lowres.pdf)).

The only support-free FDM socket design described anywhere holds a ball or knob behind 45° lips. CuteFlexi Studio's 2026 generator sets a 3 mm minimum neck, a 2.6 mm socket wall, and a socket mouth at least 0.7 mm narrower than the knob, while stating "nothing has been printed yet" ([cuteflexi-studio](https://github.com/ais80/cuteflexi-studio)).

Clearance is an absolute dimension. That is why Cenwulf scales joints separately from the body ([FlexiRex-Fusion](https://github.com/Cenwulf/FlexiRex-Fusion)), and why vendors warn that a 0.6 mm gap shrinks to an unprintable 0.3 mm at 50% scale (*secondary*, [JLC3DP](https://jlc3dp.com/blog/3d-printed-articulated-animals-design)). Material advice is anecdotal: PLA is the consensus choice, PETG needs about 0.05–0.10 mm more per side, and TPU tends to fuse (*secondary*, [Sovol](https://www.sovol3d.com/blogs/news/print-in-place-3d-printing-how-to-design-hinges-joints-and-moving-parts-that-actually-work), [MakerWorld](https://makerworld.com/de/models/2734085-flexi-trex)).

The promising bridge is AI rigging. **UniRig (MIT, 2,078 stars), MagicArticulate and Puppeteer (both Apache-2.0)** predict joints, a bone hierarchy and skinning weights for arbitrary meshes ([UniRig](https://github.com/VAST-AI-Research/UniRig), [MagicArticulate](https://github.com/Seed3D/MagicArticulate), [Puppeteer](https://github.com/Seed3D/Puppeteer)). That is exactly the "rigged 3D model" that Bächer's and Calì's 2012 pipelines took as input ([Bächer 2012](https://doi.org/10.1145/2185520.2185543), [Calì 2012](https://reality.tf.fau.de/projects/jointfit/jointfit-lowres.pdf)). In principle, joint positions say where to cut, bones give hinge axes, and skinning weights split the mesh into segments. That is an unvalidated proposal. Rig joints are kinematic centres, not fabrication-safe ones, so their positions would still need adjusting for cross-section, clearance and printability. No tool connecting the two was found. The only automatic print-in-place joint placers found are tusosos/articulated-toys, a heuristic that looks for "waists" and takes a `--clearance` flag (MIT, four stars), and an LLM pipeline that claims print-in-place mechanisms without giving numeric clearances ([articulated-toys](https://github.com/tusosos/articulated-toys), [Multi-Agent-CAD](https://github.com/Pan-Chera/Multi-Agent-CAD)).

The tolerance problem has a codifiable fix: a profile derived from printed calibration ladders, keyed by printer, nozzle, material and process settings. It would record separate XY and Z gaps, first-layer spread, a Z-seam allowance and the preferred hinge axis. It would also keep overall dimensional scaling from material shrinkage separate from hole and gap compensation; the sources give conflicting shrinkage ranges. No current generator does this; every one exposes a single clearance number. BOSL2's `$slop` test part is the closest building block ([BOSL2 constants](https://github.com/BelfrySCAD/BOSL2/wiki/constants.scad)).

### Multi-color AMS/MMU prints are governed by purge physics and sidecar files

On single-nozzle filament switchers such as Bambu's AMS, Bambu's wiki states the cost model. "In almost all cases, the number of filament changes on a single layer is one less than the number of filaments on that layer." That assumes the last filament on one layer prints first on the next; exact counts come from the sliced sequence. Flush volume depends on the color pair, with dark-to-light the worst. The prime tower must rise to the highest layer with a change. Flipping one example part so its color changes sat low cut tower material from **14.76 g to 9.05 g** ([Bambu wiki](https://wiki.bambulab.com/en/software/bambu-studio/reduce-wasting-during-filament-change)). Prusa's MMU3 takes about 42 seconds per change after its March 2026 firmware ([Prusa MMU3](https://www.prusa3d.com/en/product/original-prusa-mmu3)). Toolchangers swap in seconds; Snapmaker claims 5 s and up to 85% less waste for its U1 (vendor figures, [Snapmaker U1](https://www.snapmaker.com/snapmaker-u1)). A generator targeting AMS-class hardware should therefore cap distinct filaments per layer, keep color detail low in Z, and merge tiny regions. "Maximum colors per layer" belongs in the printer profile, because toolchangers relax it.

Encoding is where determinism and portability meet. Three encodings exist:

1. **One watertight body per color, plus slicer-specific sidecar files.** This is the most portable form.
   - Bambu Studio and OrcaSlicer read an `extruder` key per object and part from `Metadata/model_settings.config`. They treat a file as a native project only if its `Application` metadata begins with `BambuStudio-` or `OrcaSlicer-` ([bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp)).
   - PrusaSlicer reads a per-volume `extruder` from `Slic3r_PE_model.config` ([Prusa-format 3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/3mf.cpp)).
   - Cura writes and reads its own `extruder_nr` metadata ([Cura ThreeMFWriter](https://github.com/Ultimaker/Cura/blob/main/plugins/3MFWriter/ThreeMFWriter.py)).
2. **Per-triangle paint.** When color boundaries cross a single shell, painting each triangle is bit-exact and deterministic.
   - Bambu and Orca store a `paint_color` attribute whose whole-triangle codes are tabulated in their source: "4" for filament 1, "8" for 2, "0C" onward for 3–17 ([Model.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Model.cpp)).
   - PrusaSlicer uses `slic3rpe:mmu_segmentation`. It extends painted regions inward, merges thin regions it cannot print, caps painting at 16 extruders, and forbids combining painting with XY size compensation ([Prusa painting KB](https://help.prusa3d.com/article/multi-material-painting_262620)).
3. **The standard 3MF Materials extension.** This is the weakest option. Bambu and Orca map its color groups only to whole-object extruders. No evidence shows PrusaSlicer or Cura using it, and trimesh neither reads nor writes 3MF color ([bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp), [trimesh threemf.py](https://raw.githubusercontent.com/mikedh/trimesh/main/trimesh/exchange/threemf.py)).

From Python, four writers exist:

- **lib3mf** ships a color-group example ([color_cube.py](https://github.com/3MFConsortium/lib3mf/blob/master/SDK/Examples/Python/color_cube.py)).
- **build123d's `Mesher`** round-trips per-part colors and labels ([build123d](https://build123d.readthedocs.io/en/latest/import_export.html)).
- **orca123d** (MIT) writes Orca's model settings and requires Python ≥3.13, which the recommended 3.13 environment meets ([orca123d](https://pypi.org/pypi/orca123d/json)).
- **OpenSCAD's 2026.11 release candidate** adds color 3MF export on its Manifold backend ([next.md](https://github.com/openscad/openscad/blob/master/releases/next.md)), though community reports on slicer import are inconsistent (*secondary*, [Bambu forum](https://forum.bambulab.com/t/export-multicolor-design-from-openscad/232511)).

Bambu project files themselves do not travel: an issue reporting that other slicers cannot open Bambu-generated 3MFs has been open since January 2024 ([BambuStudio#3316](https://github.com/bambulab/BambuStudio/issues/3316)).

Turning a textured mesh into N printable color regions is the unsolved middle step. Bambu Studio's colored-OBJ importer already converts per-vertex colors into paint codes, with a dialog that matches them to loaded filaments ([Bambu import OBJ](https://wiki.bambulab.com/en/software/bambu-studio/import_obj), [Model.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Model.cpp)). OrcaSlicer 2.5 adds a texture import dialog that clusters texture colors, matches them to filaments and applies paint ([Plater.cpp](https://raw.githubusercontent.com/OrcaSlicer/OrcaSlicer/v2.5.0/src/slic3r/GUI/Plater.cpp)). Meshy's Multi-Color Print maps textures to AMS slots in a 3MF for 10 credits ([Meshy API pricing](https://docs.meshy.ai/api/pricing), [3DPI](https://3dprintingindustry.com/news/meshy-and-makerworld-team-up-to-put-ai-3d-model-generation-in-bambu-lab-users-hands-250281/)). But no maintained open-source tool turns a texture into N watertight per-filament shells. No source publishes a minimum paintable region size either; PrusaSlicer's merge rule for thin regions is only qualitative. For flat images the problem is easy: reduce the palette, snap it to the loaded filament colors, and extrude non-overlapping per-color bodies on a shared base.

### Multi-plate assemblies cut easily but rely on folklore tolerances

Both major slicers ship cut tools with plug, dowel and snap connectors, and Bambu adds dovetails. Neither documents a recommended tolerance ([Prusa cut tool](https://help.prusa3d.com/article/cut-tool_1779), [Bambu cut tool](https://wiki.bambulab.com/en/software/bambu-studio/cut-tool)), and forum users disagree on whether the tolerance setting changes anything (*secondary*, [Prusa forum](https://forum.prusa3d.com/forum/prusaslicer/cut-tool-doesnt-change-part-size/)). The geometry is easy to reproduce in code. manifold3d's `split_by_plane` returns both halves as guaranteed-manifold solids. Code then subtracts dowel holes from both halves and emits a separate dowel body ([manifold3d bindings](https://github.com/elalish/manifold/blob/master/bindings/python/manifold3d.cpp)). PrusaSlicer's command line also exposes `--cut` at a Z height ([prusa-slicer man page](https://dyn.manpages.debian.org/trixie/prusa-slicer/prusa-slicer.1)).

Automatic partitioning is stale. Chopper (SIGGRAPH Asia 2012) released no code. Its Python re-implementation, pychop3d (MIT, 23 stars), still says "Must use python 3.7" ([Chopper](https://pixl.cs.princeton.edu/pubs/Luo_2012_CPM/index.php), [pychop3d](https://github.com/gregstarr/pychop3d)). Layout is better done in code than by arrangement libraries: libnest2d is LGPL C++, and its Python binding pynest2d publishes no wheels ([libnest2d](https://github.com/tamasmeszaros/libnest2d), [pynest2d](https://github.com/Ultimaker/pynest2d)). Bambu and Orca record plate membership explicitly in `model_settings.config`, so a generator can assign parts to plates itself and pass `--arrange 0` to keep the slicer from rearranging them ([bbs_3mf.cpp](https://github.com/SoftFever/OrcaSlicer/blob/main/src/libslic3r/Format/bbs_3mf.cpp), [Orca cli_transform](https://github.com/OrcaSlicer/OrcaSlicer/wiki/cli_transform)).

Two practices follow from the evidence. First, orient each part with its cut face down, as both slicers' "place on cut" option does. Second, on single-nozzle machines, printing each color as a separate single-color part eliminates purge waste entirely, trading flushing for assembly. Connector clearances appear only in vendor guides, such as a 10 mm shaft in a 10.5 mm hole (*secondary*, [Sovol tolerances](https://www.sovol3d.com/blogs/news/fdm-3d-printing-tolerances-clearances-how-to-design-parts-that-fit)). The same calibration profile used for joints should therefore size connector holes.

## Treat text-to-cad as a pattern library, not a dependency

earthtojake/text-to-cad is a plugin and skill library for AI coding agents, plus a local CAD server that stays running. An agent such as Claude Code or Codex writes a build123d Python script for each part, decorated with `@model`. The server runs the script on the OpenCASCADE geometry kernel (via `cadquery-ocp-novtk` 8.x) and exports STEP, STL, 3MF, GLB or DXF ([README](https://github.com/earthtojake/text-to-cad/blob/main/README.md), [SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/SKILL.md), [PyPI cad](https://pypi.org/project/cad/)). It is MIT-licensed and was created on 22 April 2026. At **25,844 stars and 2,459 forks** it is one of the most visible CAD repositories on GitHub, and it shipped three releases on 8 November 2026 alone ([repo](https://github.com/earthtojake/text-to-cad), [releases](https://github.com/earthtojake/text-to-cad/releases)). It does not wrap Zoo's API, and it is not a neural image-to-mesh model. An agent writes parametric CAD, which the server tessellates to STL or 3MF, and its instructions treat an image only as an unscaled reference. It turns text into parametric CAD for mechanical parts, with extras for PCBs, CalculiX stress checks and OrcaSlicer slicing ([README](https://github.com/earthtojake/text-to-cad/blob/main/README.md)).

Its value to this project lies in its conventions. Its printing manufacturability check reports ([manufacturing-printing.md](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/references/manufacturing-printing.md)):

- Down-facing area below an angle limit, excluding faces resting on the plate.
- Wall thickness from 2,000 random inward rays. A hit counts only when the exit face turns at least 120° from the entry face.
- An upper-bound support-volume estimate, with the rule that ratios above about 30% of part volume justify reorienting.
- Watertightness, body count and internal voids.
- A ranking of the six axis-aligned orientations.

It also states plainly that minimum hole, minimum feature and maximum bridge "have no measured counterpart yet". Its skill text insists that "A number is never read off a picture" and "A check reports facts, never a verdict" ([SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/SKILL.md)). That is exactly the standard of evidence the requested pipeline needs. Its export guidance sets mesh tolerance to "about a tenth of the smallest clearance" and warns that a face the mesher leaves without triangles becomes a hole ([exports.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/exports.md)). Its own issue #433 was an STL export with duplicated and zero-area triangles that Bambu Studio flagged as non-manifold, fixed within a week. It shows that B-rep CAD does not guarantee watertight meshes, so a mesh check after export is still required ([issue #433](https://github.com/earthtojake/text-to-cad/issues/433)). Its catalogue of OpenCASCADE failure modes is a ready-made test list for any build123d code: fillets that silently skip edges, booleans that "return successfully" with bad geometry near tangency, and booleans that remove everything and return an empty result ([build123d-modeling.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/build123d-modeling.md)).

As a dependency it fails on fit, environment and stability:

- **Wrong design.** It solves a different problem by putting an LLM in the loop, the opposite of the requested architecture. Practitioners on Hacker News said its output "still needs heavy manual checking" (*secondary*, [HN](https://news.ycombinator.com/item?id=47970497)).
- **Incompatible Python.** The `cad` package requires **Python ≥3.14** ([PyPI cad](https://pypi.org/project/cad/)). The recommended core runs on 3.13, the only version with both Blender's `bpy` and orca123d, and point-cloud-utils has no 3.14 wheel ([verification record](../research/verification/2026-11-08-stack-smoke/README.md)). So text-to-cad needs its own interpreter. Its installer avoids the clash by fetching its own managed Python 3.14 through uv, which makes it an external tool rather than a library ([install.md](https://github.com/earthtojake/text-to-cad/blob/main/docs/install.md)).
- **Stability.** It tracks the newest OpenCASCADE wheels and carries open issues about kernel workarounds and mesh latency ([issues](https://github.com/earthtojake/text-to-cad/issues)). Its CI runs on Ubuntu and Windows, not macOS ([test.yml](https://github.com/earthtojake/text-to-cad/blob/main/.github/workflows/test.yml)).
- **Telemetry.** It sends usage statistics by default ([README](https://github.com/earthtojake/text-to-cad/blob/main/README.md)).

The verdict: use it as inspiration. It can also serve as an optional side tool, called as a separate process, for designing mechanical accessories such as stands, bases and connectors. Its MIT licence allows copying specific check code with attribution. Zoo, the other prominent text-to-CAD service, fits worse. Its Zookeeper agent "ONLY" returns code in Zoo's KCL language, and the geometry comes from a proprietary cloud engine built for NVIDIA GPUs. Its April 2026 terms let Zoo train on customer materials unless a plan allows opting out, and limit use to "internal business purposes" ([Zoo copilot docs](https://zoo.dev/docs/developer-tools/api/ml/open-a-websocket-to-a-zookeeper-agent-instance), [modeling-app](https://github.com/KittyCAD/modeling-app), [Zoo terms](https://zoo.dev/terms-and-conditions)).

The real code-CAD dependencies sit lower in the stack:

- **build123d 0.13.0 and CadQuery 2.8.0** install with pip on Apple Silicon through `cadquery-ocp` 8.0.1.1.0 arm64 wheels for CPython 3.11–3.14; both are Apache-2.0 ([cadquery-ocp](https://pypi.org/project/cadquery-ocp/), [build123d PyPI](https://pypi.org/project/build123d/)). build123d's `Mesher` is the only first-party route to multi-part, per-color 3MF; CadQuery's 3MF writer has no color ([build123d](https://build123d.readthedocs.io/en/latest/import_export.html), [CadQuery](https://cadquery.readthedocs.io/en/latest/importexport.html)).
- **OpenSCAD.** The stable 2021.01 macOS build is Intel-only. The 2026.11-RC0 tag (31 October 2026) offers a Universal binary with Manifold as the default geometry backend and color 3MF export ([OpenSCAD downloads](https://openscad.org/downloads.html), [tags](https://github.com/openscad/openscad/tags), [next.md](https://github.com/openscad/openscad/blob/master/releases/next.md)).
- **BOSL2** (BSD-2-Clause, released daily) is the deepest print-aware parametric library: snap pins, dovetails and rabbit clips calibrated by `$slop`, plus print-in-place knuckle and living hinges ([BOSL2](https://github.com/BelfrySCAD/BOSL2), [joiners.scad](https://github.com/BelfrySCAD/BOSL2/wiki/joiners.scad)).
- **bd_warehouse** covers threads, fasteners and gears for build123d. No Python library exists for snap-fits, clips or living hinges ([bd_warehouse](https://bd-warehouse.readthedocs.io/en/latest/)).

The research literature shows where LLMs belong. In Text2CAD-Bench (May 2026), frontier models produced invalid CAD on **11–20%** of simple sketch-and-extrude tasks but **68–70%** of harder tasks, reaching 70–90% for sweep, loft and shell operations; the authors also warned that a low failure rate "does not guarantee accuracy" ([Text2CAD-Bench](https://arxiv.org/abs/2605.18430)). MIRAGE-CAD reports **55.4–70.0%** build success across text, image, point-cloud and B-rep inputs ([MIRAGE-CAD](https://arxiv.org/abs/2608.28669)). Models that turn other inputs into CadQuery code exist. CAD-Recode, built on Qwen2-1.5B, works from point clouds ([CAD-Recode](https://github.com/filaPro/cad-recode)). cadrille accepts point clouds, images and text, and was trained on procedural data ([cadrille](https://arxiv.org/abs/2505.22914)). None is packaged for Apple Silicon. Every serious 2026 benchmark, including CADTests and CADEngBench, scores by running the generated program and checking the result with code ([CADTests](https://arxiv.org/abs/2605.07807), [CADEngBench](https://arxiv.org/abs/2608.09296)). The lesson for an image-to-print tool: let a model propose parameters, such as where to place hinges, which palette to use and what height to scale to, and let the deterministic gate decide.

The open gaps cluster around physical outcomes:

- **Generator quality.** No independent study measures watertightness, manifoldness or wall thickness of open image-to-3D models on a common set of images. No source quantifies first-print success for any generator.
- **Joint clearances.** No primary source gives FDM ball-and-socket dimensions from a validated print. No validated, generalizable dataset of vertical (Z) gaps exists; DrLex's hinge gives a single value. No dataset maps printer, material and profile to the minimum print-in-place gap. The only cross-printer data points are the Maryland comparison and a print-farm study whose raw numbers are not public.
- **Relief and color.** No paper validates learned depth as a source for printed bas-relief. No source publishes a minimum paintable color region relative to nozzle size, or exact default flush volumes.
- **Software behavior.** No slicer was run headless on macOS during this research. Orca and Bambu render thumbnails through OpenGL, so a session without a logged-in desktop may fail; this is inferred from source code, not tested. The CPU architecture of the Prusa and Bambu macOS installers was not confirmed. Nobody traced whether Bambu Studio honors `model_settings.config` in files that lack its `Application` tag. No 16 GB measurements exist for any 3D-generator port, and Mac support for the auto-rigging models is undocumented.
- **Safety, rights and privacy.** These were not researched: whether printed cookie cutters are safe for food contact, rights in user-supplied images, and how cloud generators retain or train on uploaded photos. Licences of whole model configurations, including bundled auxiliary weights, were recorded only in places.
- **Blocked sources.** Several hosts blocked automated fetches: MakerWorld, Printables, parts of the Bambu wiki, All3DP and MDPI. As a result, All3DP's Meshy 6 and PrintU print tests, Bambu's per-tool MakerLab export formats, and the full texts of the 2021–2025 FDM joint-clearance papers remain unread.

## Conclusion

The common framing that "AI makes 3D prints" gets the architecture backwards. Generators are becoming commodities (TRELLIS costs two cents a run) and remain untrusted suppliers whose topology can change with the hardware they run on. The lasting value sits downstream: a printer-specific tolerance profile, and a deterministic gate that accepts or rejects, repairs, measures what each repair cost, and refuses output it cannot certify. Building that gate is mostly assembly; the permissive arm64 pieces exist and were install-tested on the target machine. This survey did not find four components, and each would fill a gap:

1. Automatic splitting of a silhouette into flexi links along its medial axis.
2. A bridge from MIT/Apache rigging models to printable joints.
3. A maintained, permissively licensed, headless converter from textures to watertight AMS color regions. OrcaSlicer's import covers part of this, but it is GUI-only as far as verified, and AGPL-licensed.
4. A calibration-ladder schema that records XY, Z and first-layer clearances separately.

On a 16 GB M5, the hardware ceiling binds only at 3D generation, and it binds least where FDM asks least: single-color, shape-only meshes. That suggests an order of work. First, ship the gate and the flat, relief and flat multi-color pathways entirely locally. Second, treat photo-to-3D as a pluggable remote backend (fal, Replicate, Meshy or Tencent), with a local shape-only fallback. Throughout, keep LLMs, including agent tools like text-to-cad, in the role of proposing parameters, and require their output to pass the same gate as everything else. A Mac with 24 GB or more would unlock the TRELLIS.2 ports, but nothing in the evidence suggests local generation would be more printable, only more private.

  - **Gate:** build-volume fit and minimum dimensions are acceptance requirements, not warnings. The spec does not require a volumetric rebuild for self-intersection. A low thickness percentile is a summary, not a pass/fail rule.
  - **OrcaSlicer:** exit codes as a calling process sees them (206, 205, 197); −50 means "no suitable objects"; the triangle limit can be changed; the statistics JSON is not Linux-only; the GUI can import textures as paint.
  - **Tools that do exist:** a Python slicer wrapper (estampo, formerly fabprint).
  - **Flexi Rex:** 0.5 mm vertical and 0.55 mm radial clearance, recorded separately.
  - **BOSL2:** hinge gap and `$slop` mechanisms separated.
  - **Frohn-Sörensen 2023:** the study's conditional wording restored.
  - **Bambu:** "in almost all cases" restored to the filament-change rule.
  - **CAD-Recode:** it works from point clouds; cadrille is the model that takes images.
  - **text-to-cad:** described as agent-driven parametric CAD with mesh export.
  - **Step1X-3D:** it documents a watertight intermediate representation.
  - **Local texturing:** one textured local example on 16 GB is acknowledged.

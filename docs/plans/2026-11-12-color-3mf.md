# Multicolor 3MF writer (R2 step 3) Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** build step 3 of the R2 color design (`docs/plans/2026-11-11-color-design.md`).
`tdmg flat --colors` also writes `model.3mf`: one portable 3MF with one closed, named body
per color, which OrcaSlicer, PrusaSlicer and Bambu Studio open with the parts in place,
plus a palette manifest. It does no AMS slicing; that is step 4.

**Architecture:**
- **Writer:** a small deterministic writer, `src/tdmg/threemf.py`, writes the 3MF package
  itself with `zipfile` and `lxml`. It uses fixed timestamps, a fixed file order and
  exact float32 coordinate text, with no UUIDs unless the encoding needs them.
  - **Why not lib3mf or trimesh for writing:** both write random UUIDs (CLAUDE.md
    environment facts).
  - **lib3mf's role:** it is the independent reader in the gate.
- **Source:** the 3MF is built from exactly the AMS bodies that `ams_checks` gated.
- **Encoding:** chosen in Task 1 by real import tests, not by reading source.

**Tech stack:** zipfile, lxml, lib3mf (reader in the gate), the pinned OrcaSlicer 2.5.0
and PrusaSlicer 2.9.7 (Windows), and the owner's Bambu Studio (manual check). No new
dependency.

**Status:** written 2026-11-12; the owner approved it on 2026-11-12 ("approved").

**Format:** the repo's plan style: decisions with evidence, then tasks with tests. Every
task is test-first, gets subagent spec and quality reviews, and the Codex review comes in
Task 6.

## What is known (evidence)

- **Source reading:** `research/verification/2026-11-09-slicer-3mf-import/README.md`.
  Nothing has been import-tested yet.
  - Closed, named mesh objects are read by every slicer.
  - PrusaSlicer 2.9.7 expands an assembly (a components object) into separate objects,
    and ignores standard color tags.
  - OrcaSlicer 2.5.0 assigns a filament only from a top-level object's own `pid` (one
    color per color group).
  - Bambu Studio reads standard color groups through its own color-matching step for
    files from other programs.
- **PLAN rules:** section 2 point 7 says files are portable, using the 3MF core and
  Materials extension only, and name colors, never AMS slots. Section 4 S7 says
  "Assemblies are one components object". That conflicts with the source reading for
  PrusaSlicer, and Task 1 settles it.
- **The bodies:** step 2 gives bodies whose x and y are exact float32 numbers on the
  storage grid. So the 3MF can carry the same coordinates exactly, if they are written
  as shortest round-trip float32 text.

## Decisions

1. **Candidate encodings, measured in Task 1:**
   - **A, separate top-level objects:** one `<object>` per body, each with its own
     single-color `m:colorgroup` (`pid` on the object) and a `name` that carries the color
     (`base #f60606`, `color-1 #f5f5f5`), plus one `<item>` per object with the identity
     transform.
   - **B, one assembly:** one components object whose components are the per-color mesh
     objects, each with its color as in A.
   - **C:** A, plus a standard `m:basematerials` group with a `displaycolor` per body.

   The plan picks the encoding under which, in the pinned OrcaSlicer:
   - every body imports;
   - each body keeps its position and name;
   - each body lands on its own filament.

   In PrusaSlicer every body must import in place (its colors are ignored there, as
   known). Ties go to the simplest encoding.
   - **Result (Task 1 and the owner's Bambu Studio check, 2026-11-12):** encoding **D**,
     one mesh object with one closed shell per body, with a color on each triangle from one
     `m:colorgroup`. It is not one of A–C.
     - **Why D:**
       - in both CLIs, every separate top-level object (A, C) is dropped to the bed;
       - PrusaSlicer crashes on multi-object files;
       - D opens in place in PrusaSlicer, OrcaSlicer and the owner's Bambu Studio, and
         Bambu shows its colors;
       - the owner assigns filaments in the slicer.
     - **The 3MF manifold rule holds per shell, by vertex index.** The shells touch along
       their shared walls, which the core spec covers only as a self-intersection
       warning (`format.3mf.self_intersection_is_warning`). The record says so.
     - Evidence: `research/verification/2026-11-12-color-3mf/README.md`.
2. **Palette manifest:** a `palette.json` next to `model.3mf`. It is the guarantee,
   because standard tags are only a convenience.
   - **Per object:** the object name, its role (base or inlay), the palette index, the
     hex code, the area and the volume.
   - **Also:** the `colorflat_id` and the 3MF's SHA-256.
   - It names colors, never AMS slots (PLAN point 7).
3. **Determinism:** the same bodies give byte-identical `model.3mf` within one pinned
   environment.
   - zip entries in a fixed order with a fixed date (1980-01-01) and fixed permissions;
   - the stored or deflated choice fixed and recorded;
   - XML written by one function with a fixed attribute order;
   - no UUIDs, unless an encoding needs the Production extension (which A–C do not).
4. **A new gate check, `F2.export_3mf_matches_bodies`:** the 3MF is read back with lib3mf,
   an independent reader. With encoding D, "object" below means one shell of the single
   object, and the color is checked per triangle. The check requires:
   - unit `millimeter`;
   - one object per AMS body, with the expected names and colors;
   - each object's vertices and triangles equal to that body's gated mesh: exact,
     because both are float32;
   - lib3mf `IsManifoldAndOriented` on each object;
   - the build items as chosen.

   F1 and the occupancy check already gate the bodies, so this check only proves that the
   3MF carries them unchanged.
5. **Outputs:** `model.3mf` and `palette.json` are added to the AMS output. The AMS STLs
   stay, as a convenience. The glue output stays STL (single-color plates). The record
   (`colored.json`) lists both new files with their hashes; the algorithm label is bumped
   if the record's shape changes.
6. **Bambu Studio:** the owner opens `model.3mf` from one owner plan in Bambu Studio and
   reports whether the parts are in place and in their colors, and what the app says. This
   is a manual check, recorded verbatim; it is not a gate.

## Tasks

1. **Import experiment** (research first).
   - **Where:** `research/verification/2026-11-12-color-3mf/`.
   - **Inputs:** hand-written candidate files A, B and C from the Roadie drop plan's AMS
     bodies.
   - **OrcaSlicer 2.5.0** (pinned), with the A1 machine and process profiles and four
     copies of the pinned filament profile (`--load-filaments f;f;f;f`):
     - does it slice?
     - G-code tool changes and per-filament usage: does each body get its own filament?
     - object count and names, if reported.
   - **PrusaSlicer 2.9.7** (pinned): `--info` (object and part count, sizes, volumes) and
     a slice.
   - **Record** the commands, outputs and a verdict per encoding, then choose
     (Decision 1).
   - If no encoding gives one filament per body in OrcaSlicer, stop and report before
     Task 2.
2. **`tdmg.threemf` writer.** Tests:
   - well-formed XML against the 3MF core namespace;
   - byte-identical repeat runs;
   - exact float32 round trip of coordinates;
   - zip metadata fixed;
   - a two-cube fixture read back by lib3mf with the right names, colors and triangle
     counts.
3. **`F2.export_3mf_matches_bodies`.** Tests:
   - the gated bodies pass;
   - a 3MF with a moved vertex, a missing object, a wrong color, a wrong name or a wrong
     unit FAILs.
4. **Wire into `tdmg flat --colors`.** It writes `model.3mf` and `palette.json`, records
   both, and adds the check to the required set.
   - **Tests:** refusals unchanged; repeat runs byte-identical; the record's hashes; the
     CLI output.
   - **Owner plans:** re-run the four plans (`artifacts/colored-runs/`).
5. **Owner check in Bambu Studio** (Decision 6), recorded verbatim. A real import of the
   chosen encoding in OrcaSlicer and PrusaSlicer is also re-run on all four plans.
6. **Docs, STATUS, Codex review, push and CI.**

## Out of scope

- **AMS slicing:** the color-change count, the waste, and face up against face down
  (step 4).
- Glue plates as 3MF.
- Bambu or Orca project files (`.3mf` with slicer settings). By PLAN point 7, these would
  be an extra file only if a recipe needs one.

## Risks

- OrcaSlicer may not map standard colors to filaments at all from the CLI. In that case,
  slot assignment is a slicer-side step, and the 3MF can only name colors.
- Bambu Studio's handling is known only from its master branch source. The owner's check
  is the evidence.
